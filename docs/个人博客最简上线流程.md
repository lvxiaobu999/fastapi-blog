# 个人博客最简上线流程

这份文档只针对当前阶段的个人博客：目标是先稳定上线、能登录、能发文章、能上传图片，
不提前建设企业级平台。

文档依据仓库当前的 \`Dockerfile\`、\`compose.production.yaml\`、Nginx 模板、Settings 和
Alembic 迁移编写。命令默认在 Linux 云服务器上执行，服务器使用 Bash；本地开发仍可使用
Windows、PowerShell 和 \`uv\`。

## 1. 先确定最小架构

你现在只需要准备：

1. 一台 Linux 云服务器（1 台即可，建议至少 2 核 4 GB 内存）。
2. 一个域名，例如 \`blog.example.com\`。
3. 一个 PostgreSQL 数据库。
4. 一个 Redis 服务。
5. 一个 HTTPS 证书。

部署关系如下：

\`\`\`text
浏览器 -> 域名 DNS -> 云服务器 Nginx(80/443) -> FastAPI 容器(8000)
                                      |-> PostgreSQL
                                      |-> Redis
                                      \`-> 服务器本地 media 目录
\`\`\`

PostgreSQL 和 Redis 可以购买云厂商的最低规格托管服务，应用服务器仍然只有一台；也可以
在同一台服务器自行维护它们，但那会增加数据库备份、升级和故障处理工作。本流程按当前
仓库的生产 Compose 约定，使用“外部 PostgreSQL + 外部 Redis”，不把数据库和 Redis 写进
\`compose.production.yaml\`。

当前暂时不需要：

- 多台服务器、负载均衡、Kubernetes、CI/CD。
- RDS 高可用、Tair 集群、OSS 图片迁移。
- ELK/Loki、OpenTelemetry、自动扩容和复杂回滚编排。

这些设施以后遇到真实的流量、可用性或合规要求再增加。当前代码仍要求生产数据库使用
PostgreSQL，不能把生产环境改成 SQLite；登录续期也依赖 Redis。

## 2. 本地上线前检查

在项目根目录执行。测试数据库必须确认是隔离的测试库，不要为了上线检查直接操作需要保留
数据的业务数据库。

\`\`\`powershell
$env:PYTHONPATH = (Get-Location).Path
uv run pytest -q
uv run ruff check .
\`\`\`

如果全仓 Ruff 仍被已有问题阻塞，至少确认本次改动文件通过，并记录该问题，不要把失败结果
伪装成通过。提交一个明确的 Git tag 或 commit，服务器只部署这个版本。

## 3. 准备域名、服务器和数据库

在云厂商控制台完成以下事项：

1. 创建一台 Linux 云服务器，固定公网 IP 或 EIP。
2. 安全组只开放 \`22\`（仅你的管理 IP）、\`80\` 和 \`443\`。
3. 创建 PostgreSQL 数据库和业务账号，记录内网连接地址、端口、数据库名和账号。
4. 创建 Redis 实例和账号，记录内网连接地址、端口和密码。
5. 将服务器加入数据库和 Redis 的白名单。不要把 \`5432\`、\`6379\` 或应用的 \`8000\` 暴露到
   公网。
6. 创建 DNS A 记录：\`blog\` 指向服务器公网 IP。若使用根域名，主机记录通常填 \`@\`。

证书可以先申请云厂商的免费单域名证书并下载 Nginx 格式文件。后面需要把它们放到：

\`\`\`text
/opt/fastapi-blog/secrets/tls/fullchain.pem
/opt/fastapi-blog/secrets/tls/privkey.pem
\`\`\`

当前 Compose 启动 443 配置时要求这两个文件已经存在，所以首次上线不要跳过证书准备。

## 4. 安装 Docker 并上传代码

SSH 登录服务器后安装 Docker Engine 和 Compose 插件。不同云厂商命令可能不同，安装完成后
确认：

\`\`\`bash
docker --version
docker compose version
\`\`\`

创建部署目录并上传代码。可以使用 Git，也可以从本地复制已经确认的版本：

\`\`\`bash
sudo mkdir -p /opt/fastapi-blog/{config,data/media,secrets/tls}
sudo chown -R "$USER":"$USER" /opt/fastapi-blog
cd /opt/fastapi-blog
git clone <你的仓库地址> current
cd current
git checkout <已测试的Git_TAG或commit>
\`\`\`

如果服务器没有 Git，就在本地执行打包后使用 \`scp\` 上传；不要把 \`.env\`、证书私钥或真实
密钥一起上传到代码目录。

## 5. 创建生产配置

创建只保存 Compose 路径和域名的文件。它不包含数据库密码：

\`\`\`bash
sudo tee /opt/fastapi-blog/config/compose.env >/dev/null <<'EOF'
APP_DOMAIN=blog.example.com
APP_IMAGE_TAG=local
APP_ENV_FILE=/opt/fastapi-blog/config/app.env
MEDIA_HOST_PATH=/opt/fastapi-blog/data/media
TLS_HOST_PATH=/opt/fastapi-blog/secrets/tls
EOF
\`\`\`

再用 \`sudoedit\` 创建 \`/opt/fastapi-blog/config/app.env\`，将占位符替换成真实值：

\`\`\`dotenv
ENV=production
PROJECT_TITLE=我的个人博客
ALLOWED_HOSTS=["blog.example.com"]

DATABASE_URL=postgresql+psycopg://<数据库用户>:<URL编码后的密码>@<PostgreSQL内网地址>:5432/<数据库名>
SECRET_KEY=<至少32个字符的随机字符串>

ACCESS_TOKEN_EXPIRE_MINUTES=30
REFRESH_TOKEN_EXPIRE_MINUTES=10080
REFRESH_IDLE_TIMEOUT_MINUTES=1440
AUTH_COOKIE_SECURE=true

REDIS_URL=redis://:<URL编码后的密码>@<Redis内网地址>:6379/0
REDIS_KEY_PREFIX=fastapi-blog:production
REDIS_SOCKET_TIMEOUT_SECONDS=2

LOG_LEVEL=INFO
LOG_FORMAT=json
LOG_TO_FILE=false
\`\`\`

密码如果包含 \`@\`、\`:\`、\`/\` 或 \`#\`，必须先做 URL 百分号编码。生产 Settings 会拒绝 SQLite、
\`localhost\` Redis、短 \`SECRET_KEY\`、通配符 \`ALLOWED_HOSTS\` 和未启用 Secure Cookie 的配置。

生成 Secret 时只在服务器终端显示，不要粘贴到聊天、Git 或截图中：

\`\`\`bash
python3 -c 'import secrets; print(secrets.token_urlsafe(64))'
\`\`\`

限制配置文件权限：

\`\`\`bash
sudo chown root:root /opt/fastapi-blog/config/app.env
sudo chmod 600 /opt/fastapi-blog/config/app.env
sudo chmod 644 /opt/fastapi-blog/config/compose.env
\`\`\`

## 6. 准备媒体目录和 HTTPS 证书

容器内应用使用 UID \`10001\` 运行，宿主机媒体目录必须允许该 UID 写入：

\`\`\`bash
sudo mkdir -p /opt/fastapi-blog/data/media
sudo chown -R 10001:10001 /opt/fastapi-blog/data/media
sudo chmod 750 /opt/fastapi-blog/data/media
\`\`\`

将证书提供商下载的 Nginx 证书复制到服务器：

\`\`\`bash
sudo install -m 644 fullchain.pem /opt/fastapi-blog/secrets/tls/fullchain.pem
sudo install -m 600 privkey.pem /opt/fastapi-blog/secrets/tls/privkey.pem
sudo chown root:root /opt/fastapi-blog/secrets/tls/*.pem
\`\`\`

证书私钥不要提交 Git，也不要放入镜像。

## 7. 首次构建、迁移和启动

以后每次执行 Compose 命令都使用同一个项目目录和环境文件：

\`\`\`bash
cd /opt/fastapi-blog/current
export COMPOSE_FILE="compose.production.yaml"
export COMPOSE_ENV="/opt/fastapi-blog/config/compose.env"
\`\`\`

先确认 Compose 能解析：

\`\`\`bash
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" config -q
\`\`\`

构建应用镜像：

\`\`\`bash
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" build app
\`\`\`

第一次启动前只执行一次数据库迁移。它会按 Alembic 版本创建表，不要用 \`create_all\` 代替：

\`\`\`bash
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" run --rm app uv run alembic upgrade head
\`\`\`

迁移成功后启动应用和 Nginx：

\`\`\`bash
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" up -d
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" ps
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" logs --tail=100 app nginx
\`\`\`

预期 \`app\` 为 \`healthy\`，\`nginx\` 为 \`running\`。如果 app 一直不健康，先看日志和数据库/Redis
连接，不要用重启循环掩盖问题。

## 8. 创建管理员并做第一次验收

使用应用自带的交互式命令创建管理员，密码不会出现在命令历史：

\`\`\`bash
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" run --rm app \
  uv run python -m app.cli create-admin
\`\`\`

服务器本机先检查健康接口：

\`\`\`bash
curl -fsS "https://blog.example.com/health/live"
curl -fsS "https://blog.example.com/health/ready"
curl -I "http://blog.example.com/"
\`\`\`

预期：\`live\` 返回 \`200\`，\`ready\` 返回 \`200\`，HTTP 请求跳转到 HTTPS。如果 DNS 尚未生效，
可以临时在自己电脑的 hosts 文件中加入服务器 IP 和域名，验收后删除；不要使用 \`curl -k\`
忽略证书错误。

浏览器至少完成以下检查：

- 首页能打开，管理员能登录后台。
- 新建文章、编辑文章、发布/下架正常。
- 上传头像和帖子图片，刷新页面后仍能访问。
- 退出登录后不能继续使用旧会话。
- 普通用户访问管理员功能返回无权限，而不是只依赖前端隐藏。

## 9. 最低备份方案

个人博客先做到“能恢复”，不需要马上上复杂监控平台：

1. PostgreSQL 使用云厂商自动备份，并在每次数据库迁移前手动创建一个快照。
2. \`media\` 目录至少每周打包一次，并下载到自己的电脑或另一块存储，不能只留在服务器。
3. \`app.env\` 加密保存一份离线副本；不要把它提交 Git。

示例：

\`\`\`bash
sudo tar -czf /tmp/fastapi-blog-media-$(date +%F).tar.gz \
  -C /opt/fastapi-blog/data media
\`\`\`

然后使用 \`scp\` 将压缩包复制到服务器之外。数据库和媒体必须同时备份，只备份数据库会留下
断图，只备份媒体会留下无法查询的文件。

## 10. 以后更新博客

每次发布都按下面的顺序执行，通常几分钟即可完成：

\`\`\`bash
cd /opt/fastapi-blog/current
git fetch --tags
git checkout <新的已测试TAG或commit>
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" build app
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" run --rm app uv run alembic upgrade head
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" up -d
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" ps
\`\`\`

更新后重新打开首页、登录后台和检查一项本次改动涉及的功能。当前是单台服务器、单个 app
进程，更新期间出现几秒不可用属于预期行为。

## 11. 常见问题和禁用操作

| 现象 | 优先检查 |
| --- | --- |
| 502 Bad Gateway | \`docker compose ps\`、app 日志、Nginx 配置和健康状态 |
| readiness 503 | PostgreSQL/Redis 白名单、地址、账号和密码 URL 编码 |
| 登录或刷新失败 | Redis 是否可达；不要只把它当成密码错误 |
| 上传 413 | Nginx 当前限制约 6 MB，应用图片限制为 5 MB |
| 重启后图片消失 | \`/opt/fastapi-blog/data/media\` 是否正确挂载、UID 10001 是否可写 |
| HTTPS 启动失败 | \`fullchain.pem\`、\`privkey.pem\` 是否存在且证书域名匹配 |

生产环境不要执行：

- \`docker compose down -v\`。
- 未审查的 \`alembic downgrade\`、\`alembic stamp head\`。
- \`DROP DATABASE\`、手工删表或直接修改生产表结构。
- \`docker system prune -a --volumes\`。
- 把 \`.env\`、密码、Secret、Cookie、Token 或私钥提交 Git。

遇到故障时先保留日志和当前版本，读取 Traceback 最后一个 PostgreSQL/Redis 底层异常，再
决定修复或回滚；不要连续重启直到“看起来恢复”。

## 12. 上线完成标准

- [ ] 域名已指向服务器，80 自动跳转 443。
- [ ] app healthy、Nginx running，\`/health/live\` 和 \`/health/ready\` 通过。
- [ ] 管理员可以登录、发文、上传图片。
- [ ] PostgreSQL、Redis、媒体目录和 HTTPS 私钥位置已记录。
- [ ] 数据库自动备份已打开，媒体目录已有一次异地备份。
- [ ] 已记录当前 Git tag/commit 和下一次更新命令。

这条路线完成后，博客已经可以正式使用。只有当访问量、数据量或可用性要求明显上升时，
再单独评估 OSS、多实例、托管监控和自动发布。

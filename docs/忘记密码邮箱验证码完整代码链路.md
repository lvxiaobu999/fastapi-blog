# 忘记密码：邮箱验证码重置密码完整代码链路

本文按一次真实请求的先后顺序，说明“用户点击忘记密码”之后，浏览器、FastAPI、Pydantic、Redis、PostgreSQL、Argon2、Refresh Session 和 QQ SMTP 之间如何协作。

这份文档描述当前已经实现的代码，不包含尚未实现的 IP 限流、短信服务或邮件队列。

## 1. 功能边界与最终效果

用户不记得密码时，需要完成两次 HTTP 请求：

```text
请求验证码：POST /api/auth/password-reset/request
确认重置：  POST /api/auth/password-reset/confirm
```

重置成功后有四个结果：

1. 用户表中的 `hashed_password` 被替换为新的 Argon2 哈希；
2. Redis 中的一次性验证码被删除，原验证码不能再次使用；
3. 用户的所有 Refresh Session 被撤销，旧浏览器或旧设备不能继续刷新登录状态；
4. 现有 Access JWT 是无状态令牌，不能被 Redis 立即撤销，会继续有效到自身 `exp` 到期；前端因此清除本地 Access Token 并要求重新登录。

本功能没有新增数据库字段。验证码、过期时间和错误次数全部放在 Redis，所以不需要创建 Alembic Migration。

## 2. 总体调用关系

### 2.1 请求验证码

```text
登录页/登录弹窗
  │ 点击“忘记密码？”
  ▼
passwordResetModal（layout.html）
  │ 点击“发送验证码”
  ▼
auth.js -> ajaxRequest()
  │ POST JSON {email}
  ▼
api_auth.py -> request_password_reset_code()
  │ Depends(get_db) + Depends(get_redis)
  ▼
PasswordResetRequest（Pydantic）
  ▼
password_reset.request_password_reset()
  ├─ Redis SET cooldown（NX + EX）
  ├─ PostgreSQL 查询 users.email
  ├─ secrets 生成 6 位验证码
  ├─ HMAC-SHA256 生成验证码摘要
  ├─ Redis SET code（JSON + TTL）
  └─ email.send_password_reset_email()
       └─ AnyIO 工作线程 -> QQ SMTP 465 SSL / 587 STARTTLS
```

### 2.2 确认并重置密码

```text
用户从邮箱读取验证码
  │ 填写验证码、新密码、确认密码
  ▼
auth.js -> ajaxRequest()
  │ POST JSON {email, code, new_password, confirm_password}
  ▼
api_auth.py -> confirm_password_reset()
  ▼
PasswordResetConfirm（Pydantic）
  │ 邮箱格式、6 位数字、密码长度、两次密码一致
  ▼
password_reset.confirm_password_reset()
  ├─ Redis SET confirm-lock（NX + EX）
  ├─ Redis GET code + TTL
  ├─ HMAC 比对验证码
  ├─ 错误次数累计或删除验证码
  ├─ PostgreSQL 查询 User
  ├─ Redis 删除验证码和冷却 Key
  ├─ auth.hash_password() -> Argon2 工作线程
  ├─ refresh_sessions.revoke_user_refresh_sessions() -> Redis Lua
  └─ AsyncSession.commit() -> users.hashed_password
```

## 3. 第一步：页面和前端入口

### 3.1 页面模板

- `app/templates/login.html`：独立登录页中的“忘记密码？”链接，带有 `data-forgot-password`。
- `app/templates/layout.html`：全站登录弹窗和 `#passwordResetModal` 找回密码弹窗。
- `#passwordResetModal` 包含四类输入：注册邮箱、6 位验证码、新密码、确认新密码。

登录页和首页导航共用同一个找回密码弹窗，避免两套表单产生不同的校验规则。

### 3.2 `auth.js` 的事件链

文件：`app/static/js/auth.js`

1. `[data-forgot-password]` 点击事件阻止默认跳转；关闭登录弹窗，打开找回密码弹窗。
2. `[data-request-reset-code]` 点击事件先调用浏览器 `reportValidity()` 检查邮箱格式。
3. 通过 `ajaxRequest()` 发送 JSON 请求，不带 `auth: true`，所以忘记密码不要求用户已经登录。
4. `ajaxRequest()` 会解析项目统一成功信封，只向业务回调 `data`；验证码请求不保存响应中的任何敏感内容。
5. `[data-password-reset-form]` 提交时先在浏览器比较两次新密码，再调用确认接口。
6. 成功后重置表单、关闭找回密码弹窗、打开登录弹窗，并将邮箱填入登录标识输入框。

验证码不会写入 `localStorage`、Cookie、页面 URL 或日志。浏览器只在提交确认请求的短时间内持有用户手动输入的验证码。

## 4. Router 和依赖注入

文件：`app/routers/api_auth.py`

```python
DbSession = Annotated[AsyncSession, Depends(get_db)]
RedisClient = Annotated[Redis, Depends(get_redis)]
```

### 4.1 请求验证码 Router

`request_password_reset_code()` 做三件事：

1. 接收已通过 Schema 校验的邮箱；
2. 调用 `password_reset_service.request_password_reset()`；
3. 返回统一成功响应。

邮箱是否存在不会出现在响应中。已注册和未注册邮箱都会返回：

```json
{
  "message": "If the email is registered, a verification code has been sent",
  "data": null
}
```

邮件配置缺失或 SMTP 投递失败时，Router 将 `EmailDeliveryError` 转成 HTTP 503；不会把 SMTP 主机、账号、授权码或 Python Traceback 返回给客户端。

### 4.2 确认 Router

`confirm_password_reset()` 调用确认 Service：

- `PasswordResetCodeError` -> HTTP 400 `Invalid or expired verification code`；
- Redis 故障由全局 `RedisError` 处理器返回 HTTP 503；
- 请求体校验失败由 FastAPI 验证异常处理器返回 HTTP 422。

Router 不直接写 SQL、不生成密码哈希，也不读取 Redis Key；这些职责都留在 Service 层。

## 5. Pydantic Schema 校验

文件：`app/schemas/auth.py`

### 5.1 `PasswordResetRequest`

```python
class PasswordResetRequest(BaseModel):
    email: EmailStr = Field(max_length=254)
```

邮箱格式错误时请求不会进入 Router 的业务代码，直接返回 422。

### 5.2 `PasswordResetConfirm`

字段约束：

| 字段 | 约束 | 作用 |
| --- | --- | --- |
| `email` | `EmailStr`，最长 254 | 定位用户和验证码记录 |
| `code` | 正好 6 位 ASCII 数字 | 防止把任意字符串交给验证码 Service |
| `new_password` | 8～128 字符 | 新密码明文只在请求处理期间存在 |
| `confirm_password` | 8～128 字符 | 与新密码二次确认 |

`model_validator` 在进入 Service 前比较 `new_password` 和 `confirm_password`。不一致时返回 422，数据库和 Redis 都不会被访问。

## 6. 请求验证码 Service

文件：`app/services/password_reset.py`，函数：`request_password_reset()`。

### 6.1 邮箱标准化

邮箱先执行：

```text
strip() -> lower()
```

因此 ` User@Example.com ` 和 `user@example.com` 使用同一个数据库查询条件和 Redis Key。

### 6.2 重发冷却

Service 首先执行 Redis：

```text
SET <cooldown-key> 1 EX 60 NX
```

- `NX`：只有 Key 不存在时才成功，避免并发点击重复发信；
- `EX 60`：默认 60 秒后允许再次请求；
- 如果设置失败，Service 直接返回，不再查询用户或发送邮件。

邮箱不存在时仍保留冷却 Key，并返回成功响应，用于降低账号枚举和接口滥用风险。

### 6.2.1 `_key()` 的具体例子

`_key()` 是一个“统一生成 Redis Key 的小工具”，不是 Python 的特殊关键字。下划线开头只表示它是当前模块内部使用的辅助函数，不建议其他模块直接依赖它。

调用：

```python
normalized_email = "user@example.com"
cooldown_key = _key(normalized_email, "cooldown")
```

假设：

```text
REDIS_KEY_PREFIX=fastapi-blog
ENV=development
SHA256("user@example.com")=b4c9a289323b21a01c3e940f150eb9b8c542587f1abfd8f0e1cc1ffc5e475514
```

那么 `cooldown_key` 的完整值是：

```text
fastapi-blog:development:password-reset:cooldown:b4c9a289323b21a01c3e940f150eb9b8c542587f1abfd8f0e1cc1ffc5e475514
```

当前仓库的 `.env.development` 还把 `REDIS_KEY_PREFIX` 配置成了
`fastapi-blog:development`，所以本机实际打印出来会是：

```text
fastapi-blog:development:development:password-reset:cooldown:b4c9a289323b21a01c3e940f150eb9b8c542587f1abfd8f0e1cc1ffc5e475514
```

这里出现两段 `development` 不是 `_key()` 重复拼接参数，而是第一段来自配置的
`REDIS_KEY_PREFIX`，第二段来自 `settings.env`。如果希望 Key 更短，可以把前缀改为
`fastapi-blog`；但修改前缀会让旧 Refresh Session 和旧验证码无法再被找到，应在明确安排会话失效时再改。

同一个邮箱还会生成两个用途不同的 Key：

```text
fastapi-blog:development:password-reset:code:<同一个邮箱摘要>
fastapi-blog:development:password-reset:confirm-lock:<同一个邮箱摘要>
```

因此：

- `cooldown` 保存值通常是 `"1"`，只表示“暂时不能重复发送”；
- `code` 保存验证码 JSON，具有 10 分钟 TTL；
- `confirm-lock` 保存值通常也是 `"1"`，只有 30 秒 TTL，用于防止并发确认。

邮箱本身没有直接出现在 Key 中，防止通过 Redis Key 看到用户邮箱；`kind` 则让三个用途互不覆盖。

### 6.3 用户查询和验证码生成

已注册邮箱会通过 SQLAlchemy 异步查询：

```text
SELECT users.id, users.email, ...
FROM users
WHERE lower(users.email) = <normalized_email>
```

验证码由 `secrets.randbelow(1_000_000)` 生成，并格式化为 6 位数字，因此前导零会保留。

### 6.4 Redis 中保存的内容

Redis 不保存明文验证码，而是保存：

```json
{
  "user_id": 7,
  "email_digest": "邮箱的 SHA-256 摘要",
  "code_digest": "HMAC-SHA256(email:code)",
  "attempts": 0
}
```

验证码 Key 默认有效 600 秒。应用 `SECRET_KEY` 参与 HMAC，攻击者即使读取 Redis，也不能直接从 `code_digest` 得到验证码。

## 7. 邮件 Service 和 QQ SMTP

文件：`app/services/email.py`，入口函数：`send_password_reset_email()`。

### 7.1 配置读取

配置来自 `app/core/config.py` 的 Settings：

```text
SMTP_HOST
SMTP_PORT
SMTP_USE_SSL
SMTP_USERNAME
SMTP_PASSWORD
SMTP_FROM_EMAIL
SMTP_TIMEOUT_SECONDS
```

项目也兼容当前 `.env` 中的 `MAIL_HOST`、`MAIL_PORT`、`MAIL_USE_SSL`、`MAIL_USERNAME`、`MAIL_PASSWORD`、`MAIL_FROM`、`MAIL_FROM_NAME` 和 `PASSWORD_RESET_EXPIRE_MINUTES`。这些别名会分别映射到上述 `smtp_*` / `password_reset_code_ttl_seconds` 字段；分钟值会在 Settings 校验阶段转换为秒数。这样现有 `.env` 无需改名即可被邮件 Service 使用。

`SMTP_PASSWORD` 使用 `SecretStr`，代码不会通过 Settings 对象的 repr 输出授权码。缺少账号、授权码或发件地址时抛出 `EmailDeliveryError`。

### 7.2 为什么要使用 AnyIO 工作线程

Python 标准库 `smtplib` 是同步阻塞库。如果直接在 `async def` 中连接 QQ SMTP，网络等待会阻塞 FastAPI 事件循环。

当前实现调用：

```text
await anyio.to_thread.run_sync(_send_sync)
```

因此 SMTP 建连、登录和 `send_message()` 在工作线程中执行，不阻塞其他异步请求。

### 7.3 465 与 587

- `SMTP_PORT=465`、`SMTP_USE_SSL=true`：使用 `smtplib.SMTP_SSL`，连接建立时就启用 TLS；
- `SMTP_PORT=587`、`SMTP_USE_SSL=false`：使用 `smtplib.SMTP`，先 `EHLO`，再 `STARTTLS`，然后登录。

QQ 邮箱登录使用授权码，不使用 QQ 登录密码。邮件发送失败只抛出统一的 `EmailDeliveryError`，不会把原始 SMTP 异常传给 API 客户端。

### 7.4 发件主题和正文

邮件主题为：

```text
【三碗博客】密码重置验证码
```

邮件同时提供纯文本和 HTML 两个版本。正文包含：

- “我们收到了重置您 三碗博客 账号密码的请求”的说明；
- 单独突出显示的 6 位验证码；
- “有效期为 10 分钟，且只能使用一次”；
- “若不是本人操作请忽略，并不要向任何人透露验证码”；
- “此邮件由系统自动发送，请勿直接回复”。

HTML 版本只使用邮件正文内联样式，不加载外部图片或脚本；纯文本版本保证 QQ 邮箱或其他客户端禁用 HTML 时仍能正常阅读。验证码只插入邮件正文，不会写入主题、日志或数据库。

## 8. 确认验证码 Service

文件：`app/services/password_reset.py`，函数：`confirm_password_reset()`。

### 8.1 同邮箱确认锁

确认开始时执行：

```text
SET <confirm-lock-key> 1 EX 30 NX
```

它防止两个并发请求同时读取并消费同一个验证码。锁通过 `finally` 清理，并设置 TTL 作为异常退出时的兜底。

### 8.2 读取和校验记录

Service 依次执行：

1. Redis `GET` 验证码 JSON；
2. Redis `TTL` 检查剩余有效期；
3. 使用相同 HMAC 算法计算用户提交验证码的摘要；
4. 使用 `hmac.compare_digest()` 做定时安全比较。

验证码不存在、过期、记录损坏、邮箱摘要不一致、用户不存在或邮箱已变化，都统一抛出 `PasswordResetCodeError`。

### 8.3 错误次数

错误验证码会将 `attempts` 加一并按原 TTL 写回 Redis。达到默认 5 次时直接删除验证码，之后只能重新请求邮件。

错误详情不会告诉客户端是“验证码错误”“过期”还是“邮箱不存在”，统一返回：

```text
400 Invalid or expired verification code
```

### 8.4 密码更新和事务顺序

验证码通过后，Service 执行以下顺序：

```text
删除验证码和冷却 Key
  -> auth_service.hash_password(new_password)
  -> revoke_user_refresh_sessions(redis, user.id)
  -> session.commit()
```

`hash_password()` 使用现有 `pwdlib` Argon2 实现，并通过 AnyIO 工作线程执行 CPU 密集哈希。

撤销 Refresh Session 在数据库提交前执行。这样 Redis 不可用时会先失败，避免密码已经写入数据库但旧会话仍可继续刷新的不一致状态。

## 9. Refresh Session 撤销链路

文件：`app/services/refresh_sessions.py`

`revoke_user_refresh_sessions(redis, user_id)` 不遍历每个设备的 Session，而是提升用户级 `generation`：

```text
用户旧 Session generation = 3
密码重置后 generation = 4
```

旧 Refresh Token 中保存的 generation 与 Redis 当前 generation 不一致，因此不能再调用 `/api/auth/refresh`。旧 Session Key 会继续由自身 TTL 清理，不需要立即遍历删除。

这一步只撤销 Refresh Token，不会修改已经签发的 Access JWT；Access JWT 仍按 `exp` 到期。

## 10. Redis Key 设计

Key 中不直接放邮箱，邮箱先做 SHA-256 摘要。默认格式如下：

```text
<REDIS_KEY_PREFIX>:<ENV>:password-reset:cooldown:<email_sha256>
<REDIS_KEY_PREFIX>:<ENV>:password-reset:code:<email_sha256>
<REDIS_KEY_PREFIX>:<ENV>:password-reset:confirm-lock:<email_sha256>
```

例如生产环境前缀为 `fastapi-blog` 时，Key 类似：

```text
fastapi-blog:production:password-reset:code:...
```

Key 通过 `ENV` 隔离开发和生产，避免测试验证码读到生产 Redis 数据。

## 11. 数据和敏感信息分别存在哪里

| 数据 | 存储位置 | 生命周期 | 是否保存明文 |
| --- | --- | --- | --- |
| 用户邮箱 | PostgreSQL `users.email` | 长期 | 是业务必需数据 |
| 密码 | PostgreSQL `users.hashed_password` | 长期 | 否，只保存 Argon2 哈希 |
| 验证码摘要 | Redis | 默认 10 分钟 | 否 |
| 错误次数 | Redis 验证码 JSON | 到验证码 TTL | 是计数，不是验证码 |
| SMTP 授权码 | ECS `app.env` -> 容器环境变量 | 配置生命周期 | 不应出现在日志/Git |
| Access Token | 浏览器 `localStorage` | JWT 到期或前端清理 | 是令牌本身 |
| Refresh Token | HttpOnly Cookie + Redis 摘要 | Session TTL | Redis 不保存原始 Cookie |

验证码不会进入 PostgreSQL、Docker 镜像、前端 URL 或日志。

## 12. 异常响应链

```text
Pydantic 校验失败                  -> 422
SMTP 未配置/发送失败                 -> 503
Redis 连接、GET、SET 或 Lua 失败      -> 503
验证码不存在/错误/过期/超过次数        -> 400
数据库或未预期异常                   -> 500
```

Redis 503 由 `app/exception_handlers.py` 的 `RedisError` 处理器统一返回；客户端看不到 Redis URL、数据库密码或内部 Traceback。

## 13. 部署配置链路

### 13.1 生产域名 HTTPS

```text
/opt/fastapi-blog/config/app.env
  -> compose.production.yaml 的 env_file
  -> FastAPI 容器环境变量
  -> Settings（get_settings）
  -> email.py / password_reset.py
```

当前低成本正式方案由 ECS Docker Compose 运行 FastAPI、Nginx、PostgreSQL 和 Redis 四个容器；SMTP 是 ECS 发起的出站连接，不需要增加 SMTP Docker 容器。若未来迁移 RDS/Tair，只需替换数据库/Redis 连接配置并先完成数据迁移。

### 13.2 无域名公网 IP

使用 `compose.public-ip.yaml` 时，SMTP 配置仍放在同一个 `app.env`，接口路径和业务链路不变。变化只有 Nginx 入口是公网 IP HTTP，未配置 TLS。

公网 IP HTTP 只能用于受控联调。真实用户通过忘记密码提交新密码前，应先切换到域名 HTTPS，否则新密码会经过未加密的 HTTP。

## 14. 接口调用示例

### 14.1 请求验证码

```bash
curl -i -X POST https://<DOMAIN>/api/auth/password-reset/request \
  -H 'Content-Type: application/json' \
  -d '{"email":"user@example.com"}'
```

响应不说明账号是否存在：

```json
{
  "success": true,
  "code": 0,
  "message": "If the email is registered, a verification code has been sent",
  "data": null
}
```

### 14.2 确认重置

```bash
curl -i -X POST https://<DOMAIN>/api/auth/password-reset/confirm \
  -H 'Content-Type: application/json' \
  -d '{
    "email":"user@example.com",
    "code":"123456",
    "new_password":"new-password-123",
    "confirm_password":"new-password-123"
  }'
```

成功后使用新密码调用原有 `/api/auth/token` 登录。旧 Refresh Cookie 不应再能调用 `/api/auth/refresh`。

## 15. 推荐排查顺序

```text
1. 浏览器 Network：确认请求 URL、JSON 字段和 HTTP 状态码
2. 422：检查邮箱、验证码格式、密码长度和确认密码
3. 400：检查验证码 TTL、输入次数、邮箱大小写和是否已使用
4. 503：检查 Redis 连接，再检查 SMTP_HOST/PORT/SSL/授权码是否注入
5. SMTP 连接失败：容器内检查 smtp.qq.com DNS 和 TCP 出站策略
6. 535：重新生成 QQ 邮箱授权码，不要使用 QQ 登录密码
7. 成功但旧会话仍在：检查 Redis generation 是否已提升，并重新获取 Refresh Cookie
```

不要使用 `printenv`、完整 `docker compose config` 或日志打印 SMTP 授权码、数据库 URI、`SECRET_KEY` 和验证码。

## 16. 测试覆盖与验证

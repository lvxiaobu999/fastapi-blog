# 企业日志管理与博客实践

## 1. 日志管理解决的不是“文件放哪里”

企业日志系统主要解决六件事：

1. 关联：用 request_id、trace_id 把一次请求的多条日志串起来。
2. 检索：按 level、service、user_id、post_id 等结构化字段查询。
3. 容量：限制节点文件、采集器缓冲和平台索引，自动删除过期数据。
4. 稳定：日志平台故障不能拖慢业务请求。
5. 告警：根据错误率、延迟和关键事件通知值班人员。
6. 安全：敏感字段脱敏，限制查询权限，审计管理员操作。

目录按等级拆得很细并不等于企业级。现代日志更关注结构化字段和完整请求上下文。

## 2. 大型企业常见架构

```text
多个应用实例
  -> stdout 单行 JSON
  -> 节点日志轮转
  -> Fluent Bit / Vector / Promtail
  -> Kafka（超大规模时用于缓冲和解耦，可选）
  -> Loki / Elasticsearch / 云日志服务
  -> Grafana / Kibana / 告警平台
```

应用只负责产生日志，不在业务请求中调用“新增日志接口”。采集器负责批量、重试、背压和有限缓冲；日志平台负责查询、权限、索引和保留期。

大型企业通常还会：

- 每个服务、环境和集群添加稳定标签，例如 `service=blog-api`、`env=production`。
- 接入 OpenTelemetry，把 trace_id/span_id 注入日志并跳转到分布式 Trace。
- 将安全审计日志与普通应用日志分开授权和延长保留期。
- 对高频成功日志采样，对 ERROR 和审计事件完整保留。
- 使用指标发现问题、Trace 定位耗时、日志解释现场，而不是只靠日志监控一切。

## 3. 为什么生产环境通常不按等级写本地文件

假设请求先输出 INFO，随后输出 WARNING，最后抛 ERROR。若物理拆成五个目录，排查人员必须跨文件拼接时间线。结构化日志平台只需查询同一个 request_id：

```text
INFO  request started
INFO  user authenticated
WARNING dependency retry
ERROR post publish failed
```

此外，多 Worker 或多容器同时轮转同一个文件会产生竞争；容器重建还会丢失本地文件。因此生产使用 stdout JSON，把 `level` 当作查询字段更可靠。

## 4. 大型企业与当前博客的主要差别

| 维度 | 大型企业 | 当前博客 |
| --- | --- | --- |
| 实例数量 | 多服务、多集群、数百实例 | 当前以单体 FastAPI 为主 |
| 日志吞吐 | 每秒数万到数百万条 | 低到中等流量 |
| 关联方式 | trace_id + request_id + 服务元数据 | 已有 request_id，暂未完整接入 Trace |
| 采集链路 | Agent，必要时经过 Kafka | 尚未部署日志平台 |
| 存储 | Loki/ELK/云日志，多副本 | 开发期本地文件可满足学习和排错 |
| 告警 | 统一值班、分级告警、SLO | 后续需要增加错误率和延迟告警 |
| 审计 | 独立存储、严格权限、长期保留 | 暂无完整不可篡改审计系统 |
| 成本治理 | 采样、冷热分层、索引预算 | 先控制 DEBUG、文件大小和保留天数 |

博客不需要一开始引入 Kafka 和大型 ELK 集群，那会增加部署、内存和维护成本，却不能直接提升博客体验。架构应随流量和团队规模演进。

## 5. 当前博客采用的三种环境策略

### 本地开发

推荐直接看终端文本：

```dotenv
LOG_LEVEL=DEBUG
LOG_FORMAT=text
LOG_TO_FILE=false
```

优点是反馈即时、不产生历史文件。`aiosqlite` 和 `sqlalchemy.engine` 保持 WARNING，只看应用自己的 DEBUG。

### 单机测试或暂未部署采集器

使用一个完整日期文件：

```text
logs/YYYY-MM-DD.log
```

所有等级按发生顺序保留，level 是日志字段而不是目录。文件具有单文件大小、单日文件数和历史天数上限；这既方便按 request_id 阅读，也比无限增长的 app.log 安全。

### 正式容器生产

```dotenv
LOG_LEVEL=INFO
LOG_FORMAT=json
LOG_TO_FILE=false
```

由 Docker/Kubernetes 限制节点日志大小，由 Fluent Bit/Vector/Promtail 采集到 Loki/ELK。平台按 level 查询，不需要本地 error 文件。

## 6. 为什么博客这样做

- 保留学习价值：本地文件模式可以看到 Handler、Filter、日期和大小轮转如何工作。
- 保留完整链路：app 文件不会因等级拆分丢失请求上下文。
- 快速排错：在完整日期文件中按 level 或 request_id 搜索，不需要跨目录拼接。
- 控制容量：大小、单日数量和日期保留形成三道上限。
- 平滑上线：切换到生产只需关闭文件、启用 JSON，业务代码中的 logger 调用不变。
- 避免过度设计：当前流量不需要 Kafka 或大型日志集群，但接口已经适合未来接入。

## 7. 日志内容规范

业务代码使用稳定事件名和结构化字段：

```python
logger.info(
    "Post published",
    extra={"post_id": post.id, "user_id": current_user.id, "action": "publish"},
)
```

推荐字段包括 `request_id`、`user_id`、`post_id`、`comment_id`、`action`、`status_code` 和 `duration_ms`。禁止记录密码、Token、Cookie、完整数据库 URI、SECRET_KEY、完整请求体和不必要的个人数据。

## 8. 演进路线

```text
当前：ContextVar request_id + 本地受控轮转
  -> 部署：stdout JSON + Docker 日志上限
  -> 生产：Promtail/Vector + Loki + Grafana
  -> 扩展：OpenTelemetry trace_id/span_id
  -> 合规：独立管理员安全审计与更长保留期
```

只有日志量和服务数量显著增加、采集链路需要更强缓冲时，才考虑 Kafka、冷热存储和复杂采样策略。

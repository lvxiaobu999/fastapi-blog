# 评论模块代码逐层解析

这份文档面向第一次阅读当前评论代码的学习者。目标不是重复每一行代码，而是先建立整体模型，再解释每个文件为什么存在、函数按什么顺序调用、重要变量保存什么状态。

## 1. 先记住一条主线

发表评论的完整方向只有一条：

```text
comments.js 发送 comment.create
  -> comments.py WebSocket Router 接收并认证
  -> CommentCreateMessage 校验 JSON
  -> services/comments.py 校验回复关系并提交数据库
  -> CommentResponse 生成公开数据
  -> CommentConnectionManager 广播 comment.created
  -> comments.js 把评论插入页面
```

第一次阅读时，先忽略头像、时间格式和 CSS，只跟踪以下四个值：

```text
post_id     评论属于哪篇帖子
user_id     评论作者是谁
parent_id   用户实际回复了哪条评论
root_id     这条回复归属于哪个顶级讨论串
```

## 2. 为什么评论代码分成多层

| 层 | 文件 | 只负责什么 |
| --- | --- | --- |
| Model | `app/models/comment.py` | 描述数据库字段和 ORM 关系 |
| Schema | `app/schemas/comment.py` | 校验 WebSocket JSON，过滤公开响应 |
| Service | `app/services/comments.py` | 回复规则、查询和数据库事务 |
| Router | `app/routers/comments.py` | HTTP/WebSocket 协议、认证、错误消息 |
| 连接管理 | `app/websockets/comments.py` | 保存在线连接并广播 |
| 前端 | `app/static/js/comments.js` | 建立连接、发送消息、更新 DOM |

不要让 Router 自己拼 SQL，也不要让 Service 操作 WebSocket。分层的意义是每个文件只回答一种问题。

## 3. Model：评论在数据库里是什么

### 3.1 普通字段

```text
id          评论主键
content     评论正文，最多 1000 字符
created_at  创建时间
post_id     所属帖子
user_id     作者
```

`post_id` 和 `user_id` 都有外键及索引。删除帖子后评论不再有展示意义，因此使用 `CASCADE` 删除；删除用户时也会删除该用户评论。

### 3.2 parent_id 与 root_id

当前界面采用“二级展示、任意回复”的结构。

假设有以下讨论：

```text
评论 A
  回复 B：回复 A
  回复 C：回复 B
```

数据库保存为：

| 评论 | parent_id | root_id | 含义 |
| --- | --- | --- | --- |
| A | `NULL` | `NULL` | 顶级评论 |
| B | A.id | A.id | 直接回复 A |
| C | B.id | A.id | 实际回复 B，但仍显示在 A 的讨论串下 |

两个字段不能互相替代：

- `parent_id` 用于知道应该显示 `@谁`。
- `root_id` 用于快速知道应该把回复放进哪个顶级评论下面。

### 3.3 parent ORM 关系

`parent_id` 和 `root_id` 都指向 `comments.id`。SQLAlchemy 无法自动判断 `parent` 应该使用哪个外键，所以关系中明确写出：

```python
parent = relationship(foreign_keys=[parent_id], remote_side=[id])
```

- `foreign_keys=[parent_id]`：这个关系只使用 `parent_id`。
- `remote_side=[id]`：同一张表中，远端的 `id` 是父评论一侧。

`reply_to_author` 不是数据库字段。它通过 `parent.author` 得到被回复用户，只用于响应序列化。

## 4. Schema：WebSocket 允许传什么

### 4.1 WebSocketAuthMessage

连接建立后的第一条消息必须是：

```json
{
  "type": "authenticate",
  "token": "access-token"
}
```

`Literal["authenticate"]` 表示 `type` 只能是这个固定字符串。它让协议错误在进入业务逻辑前就被 Pydantic 拒绝。

### 4.2 CommentCreateMessage

发表评论消息是：

```json
{
  "type": "comment.create",
  "content": "评论正文",
  "parent_id": null
}
```

回复时把 `parent_id` 改成目标评论 ID。客户端不能传：

- `user_id`：必须来自验证后的 Token。
- `post_id`：必须来自 WebSocket URL。
- `root_id`：必须由 Service 根据父评论计算。

这样可以避免客户端冒充他人或伪造跨帖子关系。

### 4.3 CommentResponse

历史 HTTP 接口和 WebSocket 广播共用 `CommentResponse`。它只暴露页面需要的字段，不包含邮箱、密码哈希或 Token。

## 5. Service：评论业务规则在哪里

### 5.1 list_comments()

查询不仅加载 `Comment`，还使用 `joinedload` 提前准备：

```text
comment.author          评论作者
comment.parent.author   被回复评论的作者
```

这样 Router 创建 `CommentResponse` 时不需要再触发隐式数据库查询。在异步 SQLAlchemy 中，序列化阶段意外触发延迟加载很容易导致 `MissingGreenlet`。

### 5.2 create_comment()

按下面六步阅读：

```text
1. 查看有没有 parent_id
2. 有 parent_id 时查询同一帖子内的父评论
3. 根据父评论计算 root_id
4. 创建 Comment ORM 对象
5. commit 提交事务
6. 重新加载作者和父评论作者后返回
```

计算 `root_id` 的核心只有一行：

```python
root_id = parent.root_id or parent.id
```

解释：

- 父评论是顶级评论：`parent.root_id` 为空，因此使用 `parent.id`。
- 父评论本身是回复：它已有 `root_id`，继续沿用。

查询父评论时同时限制 `Comment.post_id == post_id`。即使客户端知道其他帖子的评论 ID，也不能跨帖子回复。

### 5.3 为什么先 commit 再广播

正确顺序：

```text
INSERT -> COMMIT -> 广播
```

如果先广播再提交，数据库提交失败时其他用户已经看到了评论，刷新后却消失。Service 负责事务，Router 只能在 Service 成功返回后广播。

## 6. Router：一条 WebSocket 连接如何运行

### 6.1 主端点只看生命周期

阅读 `comment_websocket()` 时先只看这条主线：

```text
accept
  -> 检查帖子
  -> 认证用户
  -> 注册房间
  -> while 循环接收评论
  -> 广播
  -> finally 移除连接
```

复杂步骤被拆到辅助函数中，主函数用于回答“先后顺序是什么”。

### 6.2 _authenticate_websocket()

它做四件事：

```text
1. 最多等待 10 秒接收首消息
2. 用 WebSocketAuthMessage 校验格式
3. 验证 JWT，得到 user_id
4. 查询数据库，确认用户仍存在
```

WebSocket 握手成功只代表网络连接存在，不代表用户已登录。只有这个函数返回真实 `User` 后，连接才能加入广播房间。

### 6.3 _create_comment_from_message()

一次循环只处理一条消息：

```text
receive_json
  -> CommentCreateMessage 校验
  -> comment_service.create_comment
  -> CommentResponse
```

内容错误或父评论不存在属于可恢复错误：服务端发送 `error`，但不断开连接，用户修正后可以继续发送。

### 6.4 三类服务端消息

| type | 发给谁 | 用途 |
| --- | --- | --- |
| `authenticated` | 当前连接 | 表示可以启用评论表单 |
| `comment.submitted` | 当前提交者 | 表示数据库已保存，可以解除 loading |
| `comment.created` | 整个帖子房间 | 让所有在线页面插入新评论 |

提交者也会收到 `comment.created`。前端不会在点击按钮时自己插入评论，只等待广播，因此不会重复显示。

## 7. ConnectionManager：房间是什么

内存结构可以理解为：

```python
rooms = {
    10: {socket_a, socket_b},
    20: {socket_c},
}
```

`10`、`20` 是帖子 ID。查看不同帖子的用户不会互相收到评论。

### register()

把认证成功的 WebSocket 加入 `rooms[post_id]`。

### disconnect()

移除断开的 WebSocket。如果集合变空，删除整个房间，避免无用 key 长期保留。

### broadcast()

先在锁内复制连接快照，再释放锁并执行网络发送：

```text
Lock -> 复制 sockets -> 释放 Lock -> send_json
```

网络发送可能很慢。不能拿着 Lock 等待网络，否则一个慢客户端会阻塞其他用户加入或离开房间。

当前房间只存在单个 Python 进程内。多个 Uvicorn Worker 需要 Redis Pub/Sub 才能跨进程广播。

## 8. 前端 comments.js 的状态变量

| 变量 | 保存什么 |
| --- | --- |
| `postId` | 当前详情页帖子 ID |
| `socket` | 当前 WebSocket 对象 |
| `connectionReady` | 服务端是否已经返回 authenticated |
| `submitting` | 是否有一条评论等待服务端确认 |
| `replyTarget` | 当前准备回复的评论 ID |
| `rootBodies` | 顶级评论 ID 到回复容器 DOM 的映射 |
| `pendingReplies` | 顶级评论尚未渲染时提前到达的回复 |
| `reconnectAttempts` | 已经自动重连了多少次 |

## 9. 前端启动顺序

文件最后同时执行：

```javascript
loadHistory();
connect();
```

两者并行：

- `loadHistory()` 用 HTTP 获取打开页面前已经存在的评论。
- `connect()` 用 WebSocket 接收打开页面后产生的新评论。

并行可以减少等待，但返回顺序不确定。如果 WebSocket 回复先到，而对应顶级评论还在 HTTP 响应里，`pendingReplies` 会临时保存回复，顶级评论出现后再插入。

## 10. 前端连接生命周期

```text
new WebSocket
  -> open：发送 authenticate
  -> message：按 type 分派
  -> error：关闭连接
  -> close：禁用表单并尝试重连
```

收到 `authenticated` 前，输入框和按钮保持禁用。浏览器有 Token 不代表服务端已经接受身份。

## 11. 发送评论与 loading

提交时：

```text
检查正文和 socket.readyState
  -> submitting = true
  -> 按钮显示“发送中”并禁用
  -> socket.send(comment.create)
```

收到 `comment.submitted` 后才：

```text
解除 loading
清空输入框
清除回复目标
```

如果收到 `error`，解除 loading 但保留正文，让用户修改后重试。

## 12. 建议的调试断点

按以下顺序设置断点最容易定位问题：

1. 前端 `handleCommentSubmit()`：确认发送内容和 `parent_id`。
2. Router `_create_comment_from_message()`：确认服务端收到 JSON。
3. Service `create_comment()`：确认父评论、`root_id` 和事务。
4. Manager `broadcast()`：确认房间连接数量。
5. 前端 `handleSocketMessage()`：确认收到的 `type` 和 `data`。
6. 前端 `appendComment()`：确认评论被放入正确讨论串。

## 13. 常见现象与所属层

| 现象 | 优先检查 |
| --- | --- |
| 连接后立即断开 | Router 认证、Token、帖子是否存在 |
| 评论刷新后消失 | Service 是否 commit 成功 |
| 回复显示在错误评论下 | Service 的 root_id、前端 rootBodies |
| 能保存但其他用户不实时显示 | ConnectionManager、是否多 Worker |
| 点击发送多次产生重复数据 | submitting 和按钮 loading |
| 返回数据报 MissingGreenlet | Service 是否预加载 author/parent.author |

阅读代码时始终先判断问题属于“协议、业务、数据库、广播还是 DOM”，不要从所有文件同时搜索。

# 日常发布、回滚、备份与故障处理

> 当前正式架构是 ECS 单机 Docker 四容器。RDS/Tair 相关文字属于历史托管方案；当前请重点备份
> PostgreSQL 数据目录、Redis AOF、`data/media` 和两个生产环境文件。

本文命令默认在 `/opt/fastapi-blog/current` 执行，并已定义：

```bash
export APP_DOMAIN=www.sanwan.xyz  # 必须与 compose-prod.env 和证书 SAN 一致
export COMPOSE_ENV=/opt/fastapi-blog/config/compose-prod.env
dc() { docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml "$@"; }
```

下文统一使用 `dc`。它会自动加载 `/opt/fastapi-blog/config/compose-prod.env`，避免遗漏
Compose 插值参数、数据库/Redis 密码和持久化目录。每次重新登录 ECS 后，都要先重新定义该函数。

第一次上线成功后，后续每次变更仍要重复版本、备份、迁移和验收闸门。本章不追求“命令最少”，
而是保证每次操作都知道当前版本、目标版本和恢复路径。

## 1. 日常发布前

开发/CI：

1. 完成代码评审、Ruff、格式和隔离测试。
2. 审查新 Migration，确认单一 Alembic head。
3. 产生不可变 tag/commit。
4. 写明 API、配置、数据库和 Redis 兼容性影响。
5. 确认上一个可运行 tag 和镜像仍保留。

生产：

1. 检查 ECS、PostgreSQL、Redis 容器健康和磁盘空间。
2. 记录当前 Git、镜像和 Alembic Revision。
3. PostgreSQL/Redis 数据目录备份完成；media 远端备份成功。
4. 宣布维护窗口；当前单实例发布可能短暂中断。

## 2. 记录发布前状态

```bash
cd /opt/fastapi-blog/current
git rev-parse --short HEAD
dc images
dc ps
dc run --rm app uv run --no-sync alembic current
docker system df
sudo du -sh /opt/fastapi-blog/data/media
```

这些命令不打印应用环境变量。记录输出中的版本和容量，不复制包含敏感数据的日志到公开渠道。

## 3. 获取已测试版本

```bash
git fetch --tags --prune
git checkout <RELEASE_TAG>
git status --short
export COMPOSE_ENV=/opt/fastapi-blog/config/compose-prod.env
export APP_IMAGE_TAG=$(git rev-parse --short HEAD)
```

预期工作树干净。生产服务器不执行 `git pull` 后直接运行不确定分支；明确 checkout tag/commit。

## 4. 标准发布命令

```bash
dc config -q
dc build --pull app
dc run --rm app uv run --no-sync alembic heads
dc run --rm app uv run --no-sync alembic current
```

再次确认备份完成和待执行 Migration 后：

```bash
dc run --rm app uv run --no-sync alembic upgrade head
dc up -d --remove-orphans --force-recreate
dc ps
dc logs --tail=200 app nginx postgres redis
```

验收：

```bash
curl -fsS "https://$APP_DOMAIN/health/live"
curl -fsS "https://$APP_DOMAIN/health/ready"
curl -fsS -o /dev/null -w 'HTTPS status: %{http_code}\n' "https://$APP_DOMAIN/"
dc run --rm app uv run --no-sync alembic current
```

继续用浏览器验证本次真正受影响的功能。健康接口通过不能证明登录、上传或 WebSocket 一定正常。

### 4.1 Nginx 模板或证书也发生变化

`nginx/default.conf.template` 是只读 bind mount，但 Nginx 官方镜像只在容器启动时执行环境变量
替换。仅切换 Git 文件不能保证运行中 Nginx 自动加载新内容。先用一次性容器检查：

```bash
dc run --rm --no-deps nginx nginx -t
```

通过后重建 Nginx，再检查运行中的真实配置：

```bash
dc up -d --force-recreate nginx
dc exec nginx nginx -t
```

如果只替换同路径证书，也可以在 `nginx -t` 通过后执行 `nginx -s reload`。无论哪种方式，都要
再次检查 HTTPS 证书和 WebSocket；不能先删除旧证书再尝试修新证书。

## 5. 回滚先分类

### 5.1 只改应用，未执行数据库 Migration

可以回到上一个已测试 tag：

```bash
git checkout <PREVIOUS_RELEASE_TAG>
export APP_IMAGE_TAG=$(git rev-parse --short HEAD)
dc build app
dc up -d --remove-orphans
dc ps
```

然后重复健康和业务验收。

### 5.2 执行了向后兼容 Migration

只有确认旧代码兼容新表结构时，才能只回滚应用。典型兼容迁移是先新增允许空值的字段，而旧
代码不会读取它。结论必须来自 Migration/代码审查，不能凭“看起来没问题”。

### 5.3 执行了不兼容或破坏性 Migration

不能直接 checkout 旧代码，也不能现场 `alembic downgrade`。选择之一：

- 发布向前修复版本。
- 使用仍兼容新结构的中间版本。
- 停止写流量，在隔离环境验证后恢复 PostgreSQL 备份，并同步恢复与该时间点一致的 media/配置。

数据库恢复是数据事件，应由有权限人员按照 PostgreSQL 备份恢复流程执行，并明确恢复点之后的数据损失。

## 6. 配置变更回滚

修改 `app.env` 前：

1. 加密备份旧版本到受限位置。
2. 记录改动字段和影响。
3. 使用 `sudoedit` 修改，不把 Secret 放入命令参数。
4. 运行 Settings 校验。
5. 重建/重启 app 并验收。

重要影响：

| 配置 | 轮换或修改影响 |
|---|---|
| `SECRET_KEY` | 所有现有 Access JWT 失效 |
| `REDIS_KEY_PREFIX` | 旧 Refresh Session 不可见，全员需重新登录 |
| Redis 地址/密码 | 切错会让登录/Refresh 和 readiness 失败 |
| 数据库地址/密码 | 切错会让 readiness/业务数据库请求失败 |
| `ALLOWED_HOSTS` | 域名不匹配会被 TrustedHostMiddleware 拒绝 |
| `AUTH_COOKIE_SECURE` | 生产不能设为 false，Settings 会拒绝启动 |

数据库/Redis 密码轮换要先建立新凭据、验证新连接，再废弃旧凭据，避免没有重叠窗口。

## 7. PostgreSQL 与 Redis 备份

最低策略：

- PostgreSQL 每日逻辑备份（`pg_dump`）和数据盘快照。
- Redis AOF 文件备份；它只保存会话/验证码，丢失后用户重新登录即可。
- 每次 Migration 前的手工备份。
- 备份失败告警和保留期告警。
- 定期恢复到隔离实例，验证数据库、Alembic Revision 和核心查询。

不要把 `pg_dump` 文件只存同一台 ECS 系统盘，必须加密传输到 ECS 之外的独立备份位置。

## 8. media 备份

media 与 PostgreSQL 是两套独立数据：数据库保存 URL/路径，文件在 ECS。只恢复一边会产生断图或孤儿
文件。

只读容量检查：

```bash
sudo du -sh /opt/fastapi-blog/data/media
sudo find /opt/fastapi-blog/data/media -type f | wc -l
```

备份目标应离开当前 ECS/数据盘，例如 OSS 的专用备份 Bucket。启用版本控制、生命周期和最小
权限。备份工具要保证：

- 不把 OSS 凭据写入仓库或日志。
- 删除同步默认关闭，避免本地误删传播到远端。
- 有校验和、失败告警和恢复演练。
- 记录 PostgreSQL 恢复点与 media 备份时间的对应关系。

## 9. 证书续期

证书到期前完成签发和替换：

```bash
dc exec nginx nginx -t
dc exec nginx nginx -s reload
```

正确顺序是先替换受限目录中的证书文件，再 `nginx -t`，最后 reload。替换失败保留旧证书备份，
不要重启整个应用。验证新证书 SAN、链和有效期。

## 10. 日常只读检查

```bash
dc ps
docker stats --no-stream
docker system df
dc logs --tail=200 app nginx postgres redis
dc run --rm app uv run --no-sync alembic current
sudo df -h
sudo du -sh /opt/fastapi-blog/data/media
```

关注趋势，而不是只看一次快照：容器重启次数、5xx、P95/P99、PostgreSQL 连接、Redis 延迟、磁盘增长和
证书/域名到期。

## 11. 镜像和磁盘清理

先只读查看：

```bash
docker system df
docker image ls fastapi-blog
```

保留当前和至少一个已验证回滚镜像。确认后才清理悬空层：

```bash
docker image prune
docker builder prune
```

不要把 `docker system prune -a --volumes` 当日常清理，它可能删除回滚镜像和持久卷。

## 12. 常见故障定位

统一顺序：

```text
DNS/证书
  -> ECS 安全组和 80/443
  -> Nginx 状态/配置
  -> app 容器健康
  -> Settings
  -> postgres/redis 健康、账号和密码
  -> Alembic Revision
  -> Traceback 最后一个底层异常
```

### 12.1 502 Bad Gateway

```bash
dc ps
dc logs --tail=200 app nginx postgres redis
dc exec nginx nginx -t
```

检查 app 是否 healthy、是否不断重启，以及 Nginx 是否能解析 `app:8000`。

### 12.2 readiness 503

```bash
curl -i "https://$APP_DOMAIN/health/live"
curl -i "https://$APP_DOMAIN/health/ready"
dc logs --tail=200 app
```

live 200 + ready 503 表示进程存活但 PostgreSQL/Redis 至少一个不可用。检查容器状态、账号、密码、
数据目录权限和超时。

### 12.3 登录/Refresh 503

重点检查 Redis 容器，而不是把它当密码错误：

```bash
dc logs --tail=200 app
```

日志不能包含完整 Redis URI。确认 Redis 容器健康、连接数、AOF 文件和密码配置。

### 12.4 数据库 500

```bash
dc run --rm app uv run --no-sync alembic current
dc logs --tail=200 app
```

读取最后一个 DBAPI 异常，确认数据库名、权限、连接上限和 Revision。不要直接修改生产表排错。

### 12.5 WebSocket 失败

```bash
dc logs --tail=200 nginx app
dc exec nginx nginx -T
```

确认浏览器使用 `wss://`，配置含 Upgrade/Connection Header，代理超时足够，且只有一个 app 进程。
`nginx -T` 复制到外部前也要检查内部地址等信息。

### 12.6 上传 413 或重启后丢失

```bash
dc exec nginx nginx -T
dc exec app sh -c 'id && ls -ld /app/app/media'
sudo ls -ld /opt/fastapi-blog/data/media
```

413 检查 Nginx `client_max_body_size 6m`；丢失检查挂载和 UID 10001 权限。

## 13. 扩容前的强制改造

不能直接执行 `--scale app=2`。扩容前：

1. media 改为 OSS，对象权限和 URL 契约同步修改。
2. WebSocket 广播接入 Redis Pub/Sub/Streams 或独立消息系统。
3. SLB 健康检查、真实 IP、TLS 终止和连接排空设计完成。
4. Alembic 只由单一 release job 执行。
5. 日志进入 SLS，并保持 request_id 跨层关联。
6. 验证多实例下 Refresh Token 轮换、防重放和 generation 撤销。

之后再评估多 ECS、SAE 或 ACK。

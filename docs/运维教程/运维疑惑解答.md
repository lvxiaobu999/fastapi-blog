# 运维疑惑解答：生产配置、容器参数与版本标签

本文回答四个生产部署问题：

1. 为什么使用服务器上的 /opt/fastapi-blog/config/app.env，而不是仓库里的 .env；
2. 为什么 ECS 只运行 FastAPI 和 Nginx，PostgreSQL/Redis 使用 RDS 和 Tair；
3. 如何在 ECS 上查看 Docker 参数，尤其是 UV_INDEX_URL；
4. APP_IMAGE_TAG 从哪里来，如何确认当前运行版本。

## 1. 为什么生产使用 config/app.env

当前正式 Compose 的 app 服务使用：

~~~yaml
services:
  app:
    env_file:
      - /opt/fastapi-blog/config/app.env
~~~

实际部署时路径由 APP_ENV_FILE 这个 Compose 变量决定。

### .env 和 app.env 的职责不同

仓库根目录 .env 通常用于：

- 本地开发；
- Compose 自动读取的变量替换；
- 不敏感的默认值；
- 本地 SQLite 或测试配置。

app.env 用于：

- 注入 FastAPI 容器的运行时环境；
- 保存 DATABASE_URL、REDIS_URL、SECRET_KEY 等生产配置；
- 保存生产环境域名和 RDS/Tair 内网连接信息。

关键区别：

~~~text
项目根目录 .env       -> 本地开发/Compose 变量替换
config/app.env        -> app 容器的生产运行环境
~~~

Compose 自动读取 .env 并不代表 .env 会自动进入容器。只有通过 env_file、environment 或
volume 显式配置，容器才会获得其中的值。

### app.env 的好处

#### 1. Secret 不进入 Git

生产 app.env 可能包含：

- PostgreSQL 账号和密码；
- Redis/Tair 账号和密码；
- JWT SECRET_KEY；
- 生产内部地址。

这些值应该放在服务器受限目录或密钥管理系统中，不能提交仓库。

#### 2. Secret 不进入镜像

Dockerfile 只复制代码、迁移和依赖，不复制生产 app.env。这样同一个镜像可以部署到不同环境，
换数据库密码或 JWT 密钥不需要重新构建镜像。

#### 3. 配置和代码可以独立发布

~~~text
代码版本       -> Git commit/tag、APP_IMAGE_TAG
运行配置       -> /opt/fastapi-blog/config/app.env
媒体文件       -> /opt/fastapi-blog/data/media
证书文件       -> /opt/fastapi-blog/secrets/tls
~~~

#### 4. 可以限制权限和轮换

~~~bash
sudo chown root:docker /opt/fastapi-blog/config/app.env
sudo chmod 640 /opt/fastapi-blog/config/app.env
sudo stat -c '%a %U %G %n' /opt/fastapi-blog/config/app.env
~~~

修改 app.env 后需要重新创建 app 容器：

~~~bash
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml up -d --force-recreate app
~~~

不要使用 cat app.env、env、printenv 或 docker inspect 全量输出生产配置。

## 2. ECS 为什么只运行 FastAPI 和 Nginx

推荐架构：

~~~text
浏览器
  --公网-->
ECS 公网 IP/EIP
  --> Nginx 容器（80/443、TLS、限流、WebSocket）
  --> FastAPI 容器（Compose 内网 8000）
  --> RDS PostgreSQL（VPC 私网）
  --> Tair Redis（VPC 私网）
~~~

这里的“外部 RDS/Tair”只表示它们不在 ECS 的 Docker Compose 中运行，不表示它们通过公网访问。

推荐网络路径是：

~~~text
浏览器公网 -> ECS 公网 IP/EIP -> Nginx -> FastAPI
FastAPI -> RDS/Tair VPC 私网地址
~~~

因此：

- DATABASE_URL 使用 RDS 控制台提供的 VPC 内网地址；
- REDIS_URL 使用 Tair 控制台提供的 VPC 内网地址；
- 不要使用 ECS 公网 IP 作为数据库地址；
- 不要把 RDS/Tair 公网端点作为首选；
- RDS/Tair 白名单允许 ECS 私有 IP、私网网段或安全组；
- 5432、6379、8000 不对公网开放。

使用 RDS/Tair 的好处：

- 阿里云负责实例运行、备份、监控和基础维护；
- 数据库不会与 FastAPI 抢 ECS 资源；
- ECS 重建 app/Nginx 不会直接删除数据库；
- VPC、安全组和白名单可以限制访问。

正式 compose.production.yaml 只运行 FastAPI 和 Nginx，不包含 PostgreSQL/Redis 容器和数据库密码。

如果确实在 ECS 本机用 Docker 部署数据库和 Redis，才叠加 compose.public-ip.local-services.yaml，
并让 app 使用 postgres、redis 服务名；本机方案不能和 RDS/Tair 方案混用。

## 3. 如何在 ECS 上查看 Docker 参数

先固定项目和 Compose 文件：

~~~bash
cd /opt/fastapi-blog/current
export COMPOSE_PROJECT_NAME=fastapi-blog-prod
export COMPOSE_FILE=compose.production.yaml
export COMPOSE_ENV=/opt/fastapi-blog/config/compose-prod.env
~~~

### 查看 Compose 展开的参数

~~~bash
docker compose --env-file "$COMPOSE_ENV" \
  -f "$COMPOSE_FILE" config
~~~

它会展开 APP_DOMAIN、APP_IMAGE_TAG、APP_ENV_FILE、UV_INDEX_URL、镜像、端口和挂载。

只检查 YAML 和变量替换：

~~~bash
docker compose --env-file "$COMPOSE_ENV" \
  -f "$COMPOSE_FILE" config -q
~~~

config 输出可能包含环境信息，不要完整复制到聊天或工单。

### 查看正在运行的容器和镜像

~~~bash
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" ps
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" images
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'

APP_CONTAINER=$(docker compose --env-file "$COMPOSE_ENV" \
  -f "$COMPOSE_FILE" ps -q app)

docker inspect "$APP_CONTAINER" --format '{{.Config.Image}}'
~~~

只查看非敏感运行变量：

~~~bash
docker inspect "$APP_CONTAINER" \
  --format '{{range .Config.Env}}{{println .}}{{end}}' \
  | grep -E '^(ENV|ALLOWED_HOSTS|PUBLIC_IP_MODE|AUTH_COOKIE_SECURE|LOG_LEVEL|LOG_FORMAT)='
~~~

不要直接分享完整的 docker inspect 结果，因为它可能包含数据库 URI、Redis URI 或 Secret。

### 查看 Docker daemon 参数

~~~bash
sudo cat /etc/docker/daemon.json
docker info
docker version
docker compose version
~~~

修改 daemon.json 前要备份、合并 JSON、校验格式；sudo systemctl restart docker 会影响 ECS 上所有
Docker 容器，应安排维护窗口。

## 4. UV_INDEX_URL 是什么

Dockerfile 中使用：

~~~dockerfile
ARG UV_INDEX_URL
~~~

Compose 中把 UV_INDEX_URL 传给 build.args。它是 Docker 构建阶段参数，用于告诉 uv sync 从哪个
Python 包索引下载依赖。

当前项目行为：

- 未设置：使用 uv 默认索引；
- 已设置：构建时使用指定镜像；
- 构建完成后：不会自动成为 app 容器运行时变量；
- docker inspect container 查不到它是正常的，因为 ARG 不是 ENV。

### 查看本次构建值

~~~bash
if [ -n "$UV_INDEX_URL" ]; then
  echo "UV_INDEX_URL=$UV_INDEX_URL"
else
  echo "UV_INDEX_URL 未设置，将使用 uv 默认索引"
fi

docker compose --env-file "$COMPOSE_ENV" \
  -f "$COMPOSE_FILE" config | grep -A 3 -B 2 UV_INDEX_URL
~~~

### 临时指定镜像源

~~~bash
export UV_INDEX_URL=https://mirrors.aliyun.com/pypi/simple
docker compose --env-file "$COMPOSE_ENV" \
  -f "$COMPOSE_FILE" build --pull app
~~~

PowerShell：

~~~powershell
$env:UV_INDEX_URL = "https://mirrors.aliyun.com/pypi/simple"
docker compose --env-file $env:COMPOSE_ENV -f $env:COMPOSE_FILE build --pull app
~~~

构建时也可以使用：

~~~bash
docker compose --env-file "$COMPOSE_ENV" \
  -f "$COMPOSE_FILE" build --progress=plain app
~~~

观察 uv sync 是否成功。镜像源切换只改变包下载地址，不等于 Docker DNS 已修复。

### 为什么容器里没有 UV_INDEX_URL

下面没有输出是预期的：

~~~bash
docker inspect "$APP_CONTAINER" \
  --format '{{range .Config.Env}}{{println .}}{{end}}' \
  | grep '^UV_INDEX_URL='
~~~

因为 UV_INDEX_URL 是 ARG，只在构建阶段存在。要追溯历史构建使用的镜像源，应查看部署记录、
构建命令或 CI 日志。

## 5. APP_IMAGE_TAG 从哪里来

当前 Compose 使用：

~~~yaml
image: fastapi-blog:<APP_IMAGE_TAG>
~~~

实际文件中未设置 APP_IMAGE_TAG 时会回退到 local，因此默认镜像名是：

~~~text
fastapi-blog:local
~~~

APP_IMAGE_TAG 是镜像版本标签，不是 FastAPI 业务环境变量，也不会自动从 Docker 生成。

### 推荐来源：Git commit 短 SHA

~~~bash
cd /opt/fastapi-blog/current
git status --short
git rev-parse --short HEAD
export APP_IMAGE_TAG=$(git rev-parse --short HEAD)
echo "$APP_IMAGE_TAG"
~~~

例如结果是 a1b2c3d，镜像名就是：

~~~text
fastapi-blog:a1b2c3d
~~~

优点是每个部署版本都可以反查到对应 Git 提交。

### 也可以使用 Git release tag

~~~bash
git fetch --tags --prune
git checkout v1.0.0
git status --short
export APP_IMAGE_TAG=v1.0.0
~~~

不要把 latest 作为唯一生产标识，因为它会被覆盖，无法确认具体提交。

### 构建、启动和确认版本

~~~bash
export APP_IMAGE_TAG=$(git rev-parse --short HEAD)

docker compose --env-file "$COMPOSE_ENV" \
  -f "$COMPOSE_FILE" build app

docker compose --env-file "$COMPOSE_ENV" \
  -f "$COMPOSE_FILE" up -d

docker compose --env-file "$COMPOSE_ENV" \
  -f "$COMPOSE_FILE" config | grep -E 'image: fastapi-blog:'

docker inspect "$APP_CONTAINER" --format '{{.Config.Image}}'
docker image inspect "fastapi-blog:$APP_IMAGE_TAG" \
  --format '{{.Id}} {{.Created}}'
~~~

重新设置 APP_IMAGE_TAG 不会自动更新已经运行的容器，必须重新 build 和 up。

推荐将不含 Secret 的发布参数放在：

~~~text
/opt/fastapi-blog/config/compose-prod.env
~~~

例如：

~~~dotenv
APP_DOMAIN=blog.example.com
APP_IMAGE_TAG=a1b2c3d
APP_ENV_FILE=/opt/fastapi-blog/config/app.env
MEDIA_HOST_PATH=/opt/fastapi-blog/data/media
TLS_HOST_PATH=/opt/fastapi-blog/secrets/tls
~~~

这个文件只保存域名、版本和路径，不保存数据库密码、Redis 密码或 SECRET_KEY。

## 6. 一次完整的生产发布参数示例

~~~bash
cd /opt/fastapi-blog/current
export COMPOSE_FILE=compose.production.yaml
export COMPOSE_ENV=/opt/fastapi-blog/config/compose-prod.env
export APP_IMAGE_TAG=$(git rev-parse --short HEAD)

docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" config -q
echo "commit: $(git rev-parse --short HEAD)"
echo "image tag: $APP_IMAGE_TAG"

docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" run --rm app uv run alembic current
# 备份并人工检查迁移后，再执行数据库写操作
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" run --rm app uv run alembic upgrade head

docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" build app
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" up -d
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" ps
~~~

## 7. 最终记忆表

| 内容 | 来源 | 作用 | 是否进入 app 容器运行环境 |
|---|---|---|---|
| APP_ENV_FILE | Compose 参数/Shell | 选择 env_file | 通常不是业务变量 |
| app.env | ECS 受限文件 | 注入数据库、Redis、JWT 等运行配置 | 是 |
| APP_DOMAIN | Compose 参数/Shell | 替换 Nginx 模板 | 主要给 Nginx |
| UV_INDEX_URL | Compose build args/Shell | 构建阶段下载依赖 | 否，当前是 ARG |
| APP_IMAGE_TAG | Git SHA 或 Git tag | 生成镜像标签 | 否，Compose 使用 |
| DATABASE_URL | app.env/密钥管理 | 连接 RDS PostgreSQL | 是 |
| REDIS_URL | app.env/密钥管理 | 连接 Tair Redis | 是 |
| SECRET_KEY | app.env/密钥管理 | JWT 签名 | 是 |

## 8. 四个 Compose 文件分别做什么

这四个文件不是“四套都要同时启动”的配置，而是针对不同场景的组合：

| 文件 | 场景 | 定义的服务 | 对外端口 | 数据库/Redis 来源 |
|---|---|---|---|---|
| compose.production.yaml | 正式域名、TLS 已准备 | app + nginx | 80、443 | RDS PostgreSQL + Tair Redis |
| compose.public-ip.yaml | 没有域名或证书的临时公网 IP | app + nginx | 80 | RDS/Tair，仍走 VPC 私网 |
| compose.public-ip.local-services.yaml | 公网 IP，且数据库/Redis 也在本机 Docker | postgres + redis，并为 app 增加依赖 | 不单独开放端口 | 本机 postgres/redis 容器 |
| compose.redis.development.yaml | 本地开发时只启动 Redis | redis | 只绑定 127.0.0.1:6379 | 本地 Redis 容器 |

### 8.1 compose.production.yaml：正式生产入口

它是正式域名 HTTPS 部署文件：

~~~text
Nginx 80/443 -> FastAPI app:8000 -> RDS/Tair VPC 私网
~~~

主要行为：

- 构建并运行 FastAPI app；
- 运行 Nginx；
- 80 端口跳转 HTTPS；
- 443 读取 fullchain.pem 和 privkey.pem；
- app 只使用 Compose 的 expose 暴露 8000，不映射到公网；
- app 通过 APP_ENV_FILE 读取 RDS/Tair 和 JWT 配置；
- app 健康后 Nginx 才启动；
- 用户上传目录挂载到 ECS 的 media 目录。

它不包含 PostgreSQL 容器、Redis 容器、数据库密码、Redis 密码和 5432/6379 公网端口。

使用前必须满足：

- 域名 DNS 已指向 ECS；
- APP_DOMAIN 已设置；
- ALLOWED_HOSTS 使用正式域名；
- AUTH_COOKIE_SECURE=true；
- TLS 目录有完整证书链和私钥；
- RDS/Tair 的 VPC 私网连接已经测试。

典型启动：

~~~bash
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml up -d
~~~

### 8.2 compose.public-ip.yaml：无域名临时入口

它是无域名、无证书时的 HTTP-only 入口：

~~~text
ECS 公网 IP -> Nginx:80 -> FastAPI app:8000 -> RDS/Tair VPC 私网
~~~

主要行为：

- app 和 Nginx 仍然运行；
- Nginx 只监听 80；
- 不读取 TLS 文件；
- 不监听 443；
- Nginx 使用 APP_PUBLIC_IP 替换公网 IP；
- app 仍然通过 APP_ENV_FILE 读取数据库和 Redis；
- 适用于受控内测，不适合正式运营。

app.env 通常需要：

~~~dotenv
ENV=production
ALLOWED_HOSTS=["<ECS_PUBLIC_IP>"]
PUBLIC_IP_MODE=true
AUTH_COOKIE_SECURE=false
~~~

AUTH_COOKIE_SECURE=false 是因为 HTTP 临时模式下浏览器不会发送 Secure Cookie，会带来明文传输风险。
域名和证书准备好后必须切回正式 HTTPS。

典型启动：

~~~bash
docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml up -d
~~~

如果数据库仍然使用 RDS/Tair，这个文件可以单独使用；RDS/Tair 仍通过 VPC 私网地址连接。

### 8.3 compose.public-ip.local-services.yaml：本机数据库覆盖层

这个文件不是完整 Compose，不能单独作为应用入口。它必须叠加在 compose.public-ip.yaml 后面：

~~~bash
docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml \
  -f compose.public-ip.local-services.yaml \
  up -d --build
~~~

它会额外增加：

- postgres 容器；
- redis 容器；
- postgres 数据目录挂载；
- redis 数据目录挂载；
- PostgreSQL healthcheck；
- Redis healthcheck；
- app 对 postgres 和 redis 的 depends_on 健康依赖。

本机模式的 app.env 必须把主机改成 Compose 服务名：

~~~dotenv
DATABASE_URL=postgresql+psycopg://<USER>:<PASSWORD>@postgres:5432/<DATABASE>
REDIS_URL=redis://:<PASSWORD>@redis:6379/0
~~~

Compose 参数文件还需要提供：

~~~dotenv
LOCAL_POSTGRES_USER=<USER>
LOCAL_POSTGRES_PASSWORD=<PASSWORD>
LOCAL_POSTGRES_DB=<DATABASE>
LOCAL_REDIS_PASSWORD=<PASSWORD>
PG_DATA_PATH=/opt/fastapi-blog/data/postgres
REDIS_DATA_PATH=/opt/fastapi-blog/data/redis
~~~

注意：

- postgres 和 redis 没有映射到宿主机公网端口；
- app 内部通过 Docker 网络和服务名访问它们；
- 数据目录是持久数据，必须备份；
- 这个方案由你自己负责 PostgreSQL/Redis 的升级、备份、监控和恢复；
- 使用 RDS/Tair 时不能叠加这个覆盖层；
- 只运行这个覆盖层文件是不完整的，因为它没有 Nginx 和完整 app 定义。

### 8.4 compose.redis.development.yaml：本地开发 Redis

它只适用于本地开发，不是生产部署文件。

主要行为：

- 只运行一个 Redis 容器；
- 使用 redis:7.4.2-alpine；
- 宿主机只绑定 127.0.0.1:6379；
- 使用命名卷保存开发 Redis 数据；
- 开发配置不设置密码；
- 不运行 FastAPI、Nginx 或 PostgreSQL。

启动：

~~~bash
docker compose -p fastapi-blog-dev \
  -f compose.redis.development.yaml up -d
~~~

停止：

~~~bash
docker compose -p fastapi-blog-dev \
  -f compose.redis.development.yaml stop
~~~

开发 app 通常直接由 uv/IDE 启动，连接：

~~~dotenv
REDIS_URL=redis://localhost:6379/0
~~~

不要把这个文件复制到 ECS 生产环境，因为它没有生产密码、ACL、TLS、备份和高可用能力。

## 9. 四个文件如何选择和组合

### 正式域名、RDS/Tair

只使用 compose.production.yaml，不要再叠加 public-ip 或 local-services 文件。

### 无域名公网 IP、RDS/Tair

只使用 compose.public-ip.yaml，数据库和 Redis 填写 RDS/Tair 的 VPC 私网地址。

### 无域名公网 IP、本机 Docker PostgreSQL/Redis

组合使用 compose.public-ip.yaml 和 compose.public-ip.local-services.yaml，app.env 的数据库主机填写 postgres、redis。

### 本地开发、只需要 Redis

只使用 compose.redis.development.yaml，FastAPI app 由 uv 或 IDE 启动，连接本机 127.0.0.1:6379。

### 不要这样组合

- 不要同时启动 compose.production.yaml 和 compose.public-ip.yaml，它们都会占用 80；
- 不要在正式 RDS/Tair 部署中叠加 compose.public-ip.local-services.yaml；
- 不要把 compose.redis.development.yaml 当作生产 Redis；
- 不要只启动 compose.public-ip.local-services.yaml，它不是完整入口；
- 不要让本机 Docker Redis 和 Tair 同时承担同一套生产 Refresh Session。

## 10. 如何确认实际加载了哪些服务

查看 Compose 最终服务列表：

~~~bash
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml config --services
~~~

正式模式预期：

~~~text
app
nginx
~~~

本机依赖模式：

~~~bash
docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml \
  -f compose.public-ip.local-services.yaml config --services
~~~

预期：

~~~text
app
nginx
postgres
redis
~~~

Compose 输出顺序可能不同，重点是四个服务都存在，不要把显示顺序当成启动顺序。

查看容器状态：

~~~bash
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml ps
~~~

如果看到多套项目的 app 或 nginx，先用项目名区分，不要直接删除容器。停止错误项目时使用对应
project name，避免影响正确运行的服务。

## 11. 启动命令：开发环境和生产环境

如果不熟悉命令参数，先阅读本章后面的“命令参数逐行解释”；那里把每个参数和启动结果拆开说明。

先根据场景选择配置文件：

| 场景 | 使用配置 | 启动结果 |
|---|---|---|
| 本地开发 | compose.redis.development.yaml + uv run fastapi dev | 127.0.0.1:8000 |
| 正式域名生产 | compose.production.yaml | HTTPS 域名 |
| 无域名临时生产 | compose.public-ip.yaml | HTTP 公网 IP |
| 公网 IP + ECS 本机数据库 | public-ip.yaml + public-ip.local-services.yaml | HTTP 公网 IP，附带 postgres/redis |

### 11.2 正式生产：域名 + HTTPS + RDS/Tair

正式环境准备：

~~~text
/opt/fastapi-blog/config/compose-prod.env
/opt/fastapi-blog/config/app.env
~~~

compose-prod.env 保存非敏感参数：

~~~dotenv
APP_DOMAIN=blog.example.com
APP_IMAGE_TAG=<GIT_SHA_OR_RELEASE_TAG>
APP_ENV_FILE=/opt/fastapi-blog/config/app.env
MEDIA_HOST_PATH=/opt/fastapi-blog/data/media
TLS_HOST_PATH=/opt/fastapi-blog/secrets/tls
~~~

app.env 保存生产配置：

~~~dotenv
ENV=production
ALLOWED_HOSTS=["blog.example.com"]
AUTH_COOKIE_SECURE=true
DATABASE_URL=postgresql+psycopg://<USER>:<PASSWORD>@<RDS_PRIVATE_HOST>:5432/<DATABASE>
REDIS_URL=redis://<USER>:<PASSWORD>@<TAIR_PRIVATE_HOST>:6379/0
SECRET_KEY=<RANDOM_SECRET>
~~~

在 ECS 上执行：

~~~bash
cd /opt/fastapi-blog/current
export COMPOSE_PROJECT_NAME=fastapi-blog-prod
export COMPOSE_FILE=compose.production.yaml
export COMPOSE_ENV=/opt/fastapi-blog/config/compose-prod.env
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" config -q
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" config --services
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" build --pull app
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" run --rm app uv run alembic heads
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" run --rm app uv run alembic current
# 确认数据库备份并检查迁移后，才执行数据库写操作
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" run --rm app uv run alembic upgrade head
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" run --rm --no-deps nginx nginx -t
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" up -d
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" ps
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" logs --tail=100 app nginx
~~~

正式验收：

~~~bash
curl -I https://<APP_DOMAIN>/
curl -fsS https://<APP_DOMAIN>/health/live
curl -fsS https://<APP_DOMAIN>/health/ready
~~~

### 11.3 无域名临时生产：公网 IP + RDS/Tair

使用 compose.public-ip.yaml，不要使用正式 HTTPS Compose。

compose-public-ip.env：

~~~dotenv
APP_PUBLIC_IP=<ECS_PUBLIC_IP>
APP_IMAGE_TAG=<GIT_SHA_OR_RELEASE_TAG>
APP_ENV_FILE=/opt/fastapi-blog/config/app-ip.env
MEDIA_HOST_PATH=/opt/fastapi-blog/data/media
~~~

app-ip.env：

~~~dotenv
ENV=production
ALLOWED_HOSTS=["<ECS_PUBLIC_IP>"]
PUBLIC_IP_MODE=true
AUTH_COOKIE_SECURE=false
DATABASE_URL=postgresql+psycopg://<USER>:<PASSWORD>@<RDS_PRIVATE_HOST>:5432/<DATABASE>
REDIS_URL=redis://<USER>:<PASSWORD>@<TAIR_PRIVATE_HOST>:6379/0
SECRET_KEY=<RANDOM_SECRET>
~~~

启动和验收：

~~~bash
cd /opt/fastapi-blog/current
export COMPOSE_PROJECT_NAME=fastapi-blog-ip
export COMPOSE_FILE=compose.public-ip.yaml
export COMPOSE_ENV=/opt/fastapi-blog/config/compose-public-ip.env
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" config -q
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" build --pull app
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" run --rm app uv run alembic current
# 确认目标数据库和备份后执行
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" run --rm app uv run alembic upgrade head
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" up -d
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" ps
curl -fsS http://<ECS_PUBLIC_IP>/health/live
curl -fsS http://<ECS_PUBLIC_IP>/health/ready
~~~

这是临时 HTTP 模式，Cookie 和 Token 可能被明文窃听。备案和证书完成后切换到 compose.production.yaml，
并恢复 AUTH_COOKIE_SECURE=true。

### 11.4 公网 IP + ECS 本机 PostgreSQL/Redis

本机依赖必须叠加两个 Compose 文件：

~~~bash
cd /opt/fastapi-blog/current
export COMPOSE_PROJECT_NAME=fastapi-blog-ip
export COMPOSE_ENV=/opt/fastapi-blog/config/compose-public-ip.env
docker compose --env-file "$COMPOSE_ENV" -f compose.public-ip.yaml -f compose.public-ip.local-services.yaml config --services
~~~

预期包含 app、nginx、postgres、redis。参数文件还要提供：

~~~dotenv
LOCAL_POSTGRES_USER=<USER>
LOCAL_POSTGRES_PASSWORD=<PASSWORD>
LOCAL_POSTGRES_DB=<DATABASE>
LOCAL_REDIS_PASSWORD=<PASSWORD>
PG_DATA_PATH=/opt/fastapi-blog/data/postgres
REDIS_DATA_PATH=/opt/fastapi-blog/data/redis
~~~

app-ip.env 的数据库主机必须是 Compose 服务名：

~~~dotenv
DATABASE_URL=postgresql+psycopg://<USER>:<PASSWORD>@postgres:5432/<DATABASE>
REDIS_URL=redis://:<PASSWORD>@redis:6379/0
~~~

启动：

~~~bash
docker compose --env-file "$COMPOSE_ENV" -f compose.public-ip.yaml -f compose.public-ip.local-services.yaml up -d --build
docker compose --env-file "$COMPOSE_ENV" -f compose.public-ip.yaml -f compose.public-ip.local-services.yaml ps
~~~

确认 postgres 和 redis healthy 后，再执行 alembic upgrade head。

~~~bash
# 备份并审查迁移后执行
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" run --rm app uv run alembic upgrade head
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" up -d
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" ps
~~~

常用状态命令：

~~~bash
docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" ps

docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" restart app
~~~

## 12. 命令参数逐行解释

看到一条 Compose 命令时，可以按这个顺序阅读：

~~~text
docker compose
  -> 调用 Docker Compose
-p 项目名
  -> 给这套容器分组，避免不同环境互相混淆
--env-file 文件
  -> 提供 Compose 替换变量，例如 APP_ENV_FILE、APP_IMAGE_TAG、APP_DOMAIN
-f 文件
  -> 指定 Compose 配置文件
多个 -f
  -> 按顺序合并配置，后面的文件覆盖或补充前面的文件
up
  -> 创建并启动服务
-d
  -> 后台运行，不占用当前终端
--build
  -> 启动前重新构建有 build 配置的镜像
ps
  -> 只查看服务状态，不启动或修改服务
~~~

### 12.1 逐行解释本机 PostgreSQL/Redis 启动命令

原命令：

~~~bash
docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml \
  -f compose.public-ip.local-services.yaml \
  up -d --build
~~~

逐行说明：

~~~text
docker compose
  调用 Docker Compose，而不是直接调用单个 docker run。

-p fastapi-blog-ip
  设置 Compose 项目名。容器通常会带有这个项目名，后续 ps、logs、stop
  只操作 fastapi-blog-ip 这一组服务，不会误操作正式生产项目。

--env-file /opt/fastapi-blog/config/compose-public-ip.env
  指定 Compose 的变量文件。它用于解析 APP_PUBLIC_IP、APP_IMAGE_TAG、
  APP_ENV_FILE、MEDIA_HOST_PATH、LOCAL_POSTGRES_* 等变量。
  这个文件不是 app.env；app.env 的路径由 APP_ENV_FILE 指向，再由 app 服务的 env_file 注入容器。

-f compose.public-ip.yaml
  加载公网 IP 基础配置，提供 app 和 nginx 两个服务。
  Nginx 只监听 80，FastAPI 的 8000 只在 Compose 网络中暴露。

-f compose.public-ip.local-services.yaml
  加载本机依赖覆盖层，增加 postgres 和 redis 服务，并让 app 等待它们的
  healthcheck 通过。后面的文件是补充配置，不是独立完整入口。

up
  创建不存在的容器，必要时重新创建配置发生变化的容器，然后启动服务。
  它会根据 depends_on 的健康条件先启动 postgres/redis，再启动 app，最后启动 nginx。

-d
  detached，后台运行。命令执行后终端立即返回，可以用 ps 和 logs 查看结果。

--build
  启动前构建 app 镜像。它不会把 PostgreSQL 或 Redis 变成镜像，
  这两个服务仍然直接使用 compose 文件中声明的官方镜像。
~~~

启动后查看状态：

~~~bash
docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml \
  -f compose.public-ip.local-services.yaml \
  ps
~~~

这条命令只查看状态：

~~~text
docker compose
  仍然选择 Compose 工具
-p fastapi-blog-ip
  只查看公网 IP + 本机依赖这一组容器
--env-file 和两个 -f
  必须与启动时保持一致，否则可能查看到另一套项目或无法解析变量
ps
  显示 app、nginx、postgres、redis 的运行状态、健康状态和端口
~~~

常见结果：

- postgres、redis 为 healthy：本机依赖已经通过自己的健康检查；
- app 为 healthy：FastAPI 的 /health/ready 已成功检查数据库和 Redis；
- nginx 为 running：Nginx 已经可以接收公网请求；
- app 为 unhealthy：先看 app 日志和 /health/ready，不要反复重启；
- nginx 没有启动：通常是 app 尚未 healthy、80 端口冲突或 Nginx 配置错误。

### 12.2 正式生产命令逐行解释

~~~bash
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml \
  up -d
~~~

说明：

- fastapi-blog-prod：正式生产项目名；
- compose-prod.env：非敏感的域名、镜像标签、app.env 路径、媒体目录和证书目录；
- compose.production.yaml：只启动 app 和 nginx；
- app 的数据库和 Redis 由 app.env 指向 RDS/Tair 私网地址；
- up -d：后台启动；
- 这里没有 --build，因此使用现有镜像；发布新代码时要先执行 build 或使用 up -d --build。

正式生产构建新版本：

~~~bash
# 生成当前 Git 提交对应的镜像标签
export APP_IMAGE_TAG=$(git rev-parse --short HEAD)

# 重新构建 app 镜像，不启动容器
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml \
  build --pull app

# 后台启动或更新 app/nginx
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml \
  up -d
~~~

其中：

- git rev-parse --short HEAD：读取当前源码提交的短 SHA；
- build：根据 Dockerfile 构建新 app 镜像；
- --pull：构建前尝试拉取更新的基础镜像；
- up -d：使用新镜像创建或更新容器；
- 这组命令不会自动执行 Alembic，数据库迁移需要单独确认后执行。

### 12.3 无域名公网 IP 命令逐行解释

~~~bash
docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml \
  up -d
~~~

说明：

- 只加载 app 和 Nginx；
- Nginx 只监听 80；
- APP_PUBLIC_IP 用于替换 Nginx 的 server_name；
- app.env 仍然可以连接 RDS/Tair 私网；
- 没有证书，不会监听 443；
- 这是临时 HTTP 入口，不是正式 HTTPS 部署。

### 12.4 其他常用命令解释

~~~bash
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml \
  config -q
~~~

config -q：只检查 YAML 和变量替换，成功时通常没有输出；不会启动容器，也不会连接数据库。

~~~bash
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml \
  config --services
~~~

config --services：只列出最终配置包含的服务。正式模式应看到 app、nginx；本机依赖模式还应看到
postgres、redis。

~~~bash
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml \
  logs --tail=200 app nginx
~~~

logs --tail=200：查看 app 和 nginx 最近 200 行日志，不会修改容器。排查 503、502、启动失败时优先使用。

~~~bash
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml \
  restart app
~~~

restart app：重启已有 app 容器，不重新构建镜像，不重新读取 Git 代码。适合临时恢复进程；修改镜像或
环境变量后应使用 build 和 up，必要时加 --force-recreate。

~~~bash
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml \
  stop
~~~

stop：停止容器但保留容器、镜像和数据。之后可以用 start 恢复。

~~~bash
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml \
  run --rm app uv run alembic current
~~~

run --rm app：临时创建一个 app 容器，执行后删除临时容器；这里的 alembic current 只查看数据库当前
迁移版本。

~~~bash
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml \
  run --rm app uv run alembic upgrade head
~~~

这条命令会修改 PostgreSQL 数据库结构，是数据库写操作。执行前必须确认目标数据库、备份和迁移内容，
不能把它当作普通启动命令。

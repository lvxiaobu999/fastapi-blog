# 首次部署与数据库迁移

本章第一次启动 ECS Docker 中的 PostgreSQL/Redis，并写入数据库结构。开始前应完成前四章，已上传
`/opt/fastapi-blog/config/compose-prod.env`，并在当前 shell 设置 `COMPOSE_ENV` 与
`APP_IMAGE_TAG`。后续命令统一通过 `--env-file` 读取该 Compose 配置。

请先按 [04-ECS 初始化与生产配置](04-ECS初始化与生产配置.md#6-配置-compose-参数) 上传并配置
`compose-prod.env`；`app.env` 由 Compose 的 `services.app.env_file` 注入容器，两个文件职责不同。

```bash
export COMPOSE_FILE=compose.production.yaml
export COMPOSE_ENV=/opt/fastapi-blog/config/compose-prod.env
test -r "$COMPOSE_ENV"
```

## 1. 上线窗口开始前

记录：

```text
发布 tag/commit：
镜像 Image ID：
Alembic 目标 head：
PostgreSQL 数据目录：/opt/fastapi-blog/data/postgres
目标数据库名：fastapi_blog_postgresql
最近逻辑/目录备份：
本次备份文件及复制到 ECS 外的完成时间：
执行人：
复核人：
回滚候选 tag：
```

备份必须已经完成，不是只点击了“创建备份”。首次空库也要确认实例和数据库目标，养成同一套
发布习惯。

## 2. 再次确认版本和配置

```bash
cd /opt/fastapi-blog/current
git status --short
git rev-parse --short HEAD
printf '%s\n' "$APP_IMAGE_TAG"
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml config -q
```

预期：

- Git 工作树没有修改。
- commit 短 SHA 与 `APP_IMAGE_TAG` 一致。
- Compose 解析无错误。

不要用 `env`、`printenv`、`docker inspect` 全量输出环境变量来确认配置。

## 3. 先启动 PostgreSQL/Redis

```bash
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml up -d postgres redis
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml ps postgres redis
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml logs --tail=100 postgres redis
```

预期两个服务为 `healthy`。它们只在 Compose `backend` 网络可见，ECS 不应公开 5432/6379。

## 4. 迁移前只读检查和连接验证

查看镜像中的迁移链，不连接数据库：

```bash
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml run --rm app uv run --no-sync alembic heads
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml run --rm app uv run --no-sync alembic history
```

`heads` 应只有一个目标 head。然后连接本机生产 PostgreSQL，只读取当前 Revision：

```bash
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml run --rm app uv run --no-sync alembic current
```

首次空数据库可能没有当前 Revision 输出；已有数据库必须和发布记录中的预期一致。如果发现
数据库比预期新、出现多个 head、连接到错误名称或无法解释的表，立即停止。

### 4.1 验证应用连接

在一次性 app 容器中执行最小只读检查，不打印地址和凭据：

```bash
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml run --rm -T app uv run --no-sync python - <<'PY'
import asyncio

from sqlalchemy import text

from app.db.session import engine


async def main() -> None:
    async with engine.connect() as connection:
        await connection.execute(text("SELECT 1"))
    await engine.dispose()
    print("database: ok")


asyncio.run(main())
PY
```

Redis 检查：

```bash
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml run --rm -T app uv run --no-sync python - <<'PY'
import asyncio

from app.db.redis import redis_client


async def main() -> None:
    await redis_client.ping()
    await redis_client.aclose()
    print("redis: ok")


asyncio.run(main())
PY
```

`-T` 关闭伪终端，让 heredoc 中的 Python 源码可以通过标准输入传入容器。如果当前 shell 不支持
这种 heredoc，可以跳过这两条，后面的 `/health/ready` 会检查同样依赖；不要为了改写命令而
输出 URI。

## 5. 执行 Alembic Upgrade

高风险写操作，只由一个发布终端执行一次：

```bash
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml run --rm app uv run --no-sync alembic upgrade head
```

它会：

```text
读取本机生产 PostgreSQL 当前 alembic_version
  -> 按 down_revision 顺序执行尚未应用的 upgrade()
  -> 创建/修改业务表和必要数据
  -> 将 alembic_version 更新到 head
```

成功后立即确认：

```bash
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml run --rm app uv run --no-sync alembic current
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml run --rm app uv run --no-sync alembic heads
```

两者应指向同一 head。

### 5.1 如果迁移失败

停止，不要连续重试。按顺序处理：

1. 保存完整内部日志，但对外分享前删除 Host、用户名和路径等敏感信息。
2. 阅读 Traceback 最后一个 PostgreSQL/DBAPI 异常，而不是停在 SQLAlchemy 第一层。
3. 再确认 PostgreSQL 数据目录、数据库名、账号权限、当前 Revision 和失败 Migration。
4. 判断事务是否已经回滚，以及 Migration 是否含非事务或数据操作。
5. 在隔离数据库复现并制定向前修复或恢复方案。

禁止用这些命令“消除报错”：

```text
alembic stamp head
alembic downgrade ...
手工删除表/字段
修改已经执行过的旧 Migration
```

## 6. 启动 Compose

迁移成功后：

```bash
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml up -d --force-recreate
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml ps
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml logs --tail=100 app nginx
```

这三条命令的作用不同：

| 命令 | 作用 | 是否修改业务数据 |
|---|---|---|
| `up -d` | 按当前 Compose 配置创建或更新 `app`、`nginx` 容器，并在后台运行；Nginx 会等待 `app` 健康后再启动 | 可能创建/重建容器，不会主动修改业务表 |
| `ps` | 查看容器是否为 `healthy`/`running`，确认 app readiness 和 Nginx 状态 | 否 |
| `logs --tail=100 app nginx` | 查看最近 100 行应用和 Nginx 日志，用于判断启动失败、502 或证书错误 | 否 |

`up -d` 使用本章前面设置的 `APP_DOMAIN`、`APP_IMAGE_TAG`、`APP_ENV_FILE`、`MEDIA_HOST_PATH`
和 `TLS_HOST_PATH`。如果新开了 SSH 会话，必须先重新设置这些变量；否则 Compose 可能找不到
生产环境文件、证书目录或镜像标签。不要因为容器未健康就反复执行迁移或使用 `down -v`，应先
查看日志最后一个数据库/Redis 异常。

Compose 行为：

1. app 容器启动单个 FastAPI 进程。
2. app readiness 执行数据库 `SELECT 1` 和 Redis `PING`。
3. app 健康后 Nginx 才启动。
4. Nginx 在宿主机监听 80/443。
5. FastAPI 8000 只 `expose` 到 Compose 内部网络，不映射宿主机公网。

### 6.1 静态资源发布检查

`app/static` 已经包含在 `app` 镜像中，不需要也不应该同步到 `/opt/fastapi-blog/data/static`。
宿主机只保存 `data/media`（用户上传）、`secrets/tls`（证书）和 `config/app.env`（运行时配置）。
每次发布必须先执行 `build app`，再启动容器；否则 Compose 可能复用上一次构建的镜像，浏览器看到的
仍是旧 CSS/JS 或旧 Logo。

启动后可以做只读检查：

```bash
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml exec app sh -c \
  'test -f /app/app/static/css/site.css && \
   test -f /app/app/static/images/logo.png && \
   test -f /app/app/static/images/favicon.ico'
curl -fsSI "https://$APP_DOMAIN/static/css/site.css"
curl -fsSI "https://$APP_DOMAIN/static/images/logo.png"
curl -fsSI "https://$APP_DOMAIN/static/images/favicon.ico"
```

若 `test` 通过而 `curl` 失败，优先检查当前运行的 Compose 文件和 Nginx 容器是否来自同一个发布目录，
以及是否存在旧的 `/app/app/static` 宿主机挂载；不要手工把文件复制到 `data/static`。

`docker compose ps` 中 app 应为 healthy，Nginx 应为 running。

## 7. 容器内部健康检查

使用与 Compose healthcheck 相同的 Host Header：

```bash
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml exec app uv run --no-sync python -c \
  "import json, os, urllib.request; host=json.loads(os.environ['ALLOWED_HOSTS'])[0]; \
request=urllib.request.Request('http://127.0.0.1:8000/health/ready', headers={'Host': host}); \
print(urllib.request.urlopen(request, timeout=3).read().decode())"
```

预期：

```json
{"status":"ready"}
```

如果 liveness 正常但 readiness 503，进程还活着，问题在 PostgreSQL/Redis 容器状态或凭据，不应通过重启
循环掩盖。

## 8. Nginx 本机前置验收

无需等待公共 DNS，使用 `--resolve` 把正式域名临时指到本机：

```bash
curl -I --resolve "$APP_DOMAIN:80:127.0.0.1" "http://$APP_DOMAIN/"
curl -fsS -o /dev/null -w 'HTTPS status: %{http_code}\n' \
  --resolve "$APP_DOMAIN:443:127.0.0.1" "https://$APP_DOMAIN/"
curl -fsS --resolve "$APP_DOMAIN:443:127.0.0.1" \
  "https://$APP_DOMAIN/health/live"
curl -fsS --resolve "$APP_DOMAIN:443:127.0.0.1" \
  "https://$APP_DOMAIN/health/ready"
```

预期：

- HTTP 返回 301 到固定 HTTPS 域名。
- HTTPS 使用真实 GET 请求返回 200，且证书与 `$APP_DOMAIN` 匹配。
- live 返回 `{"status":"ok"}`。
- ready 返回 `{"status":"ready"}`。

不要使用 `curl -k` 忽略证书错误完成正式验收；证书链或域名错误必须修复。

## 9. 验证 media 挂载

确认挂载：

```bash
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml exec app sh -c \
  'id && mount | grep /app/app/media || true; ls -ld /app/app/media'
```

做一次可恢复写入测试：

```bash
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml exec app sh -c \
  'touch /app/app/media/.write-test && rm /app/app/media/.write-test'
```

然后确认宿主目录仍存在。失败时修正 UID 10001 的目录权限，不使用容器可写层替代挂载。

## 10. 创建生产管理员

这是生产数据库写操作：

```bash
docker compose --env-file "$COMPOSE_ENV" -f compose.production.yaml run --rm app \
  uv run --no-sync python -m app.cli create-admin
```

交互输入用户名、邮箱和密码。密码不写进命令参数或脚本。创建后使用浏览器验证管理员接口，
不要通过 SQL 手工把普通用户改成管理员。

## 11. 暂不切 DNS 时的访问方式

在管理员电脑的 hosts 文件临时添加：

```text
<ECS_PUBLIC_IP> <APP_DOMAIN>
```

或者继续使用 `curl --resolve`。内测期间可让安全组 80/443 只允许管理员 IP。修改 hosts 后要
记得删除，避免以后误判 DNS。

大陆节点在备案和页面展示等前置未完成时，不应直接向公众开放。

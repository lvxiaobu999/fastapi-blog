# 运维疑惑解答：ECS 单机 Docker 生产方案

> 当前正式方案已经确定为一台 ECS 上的 Docker Compose 四容器：`app`、`nginx`、`postgres`、`redis`。
> 不需要购买 RDS/Tair。本文中提到 RDS/Tair 的地方只用于说明未来迁移思路，不能作为当前启动命令。
> 生产命令默认在 ECS Linux Bash 执行；Windows PowerShell 只用于本地预检。

## 1. 为什么要使用两个环境文件

生产服务器上有两个职责不同的文件：

| 文件 | 用途 | 由谁读取 | 应保存什么 |
| --- | --- | --- | --- |
| `/opt/fastapi-blog/config/compose-prod.env` | Compose 插值参数 | `docker compose --env-file` | 域名、镜像标签、数据目录、PostgreSQL/Redis 密码 |
| `/opt/fastapi-blog/config/app.env` | FastAPI 运行时配置 | `services.app.env_file` | `ENV`、`SECRET_KEY`、Cookie、邮件、OAuth、限流等应用配置 |

`compose.production.yaml` 会依据第一个文件自动生成并注入：

```text
DATABASE_URL=postgresql+psycopg://<user>:<password>@postgres:5432/<db>
REDIS_URL=redis://:<password>@redis:6379/0
```

因此 `app.env` 不再重复保存 `DATABASE_URL`、`REDIS_URL`。这可以避免两个文件的密码不一致，
也意味着脱离 Compose 直接运行 `uv run fastapi ...` 不适用于生产：此时不会自动得到连接串。

仓库提供不含密钥的 [`deploy/compose-prod.env.example`](../../../deploy/compose-prod.env.example)。
复制后填写真实密码，再上传到服务器；真实文件已在 `.gitignore` 中，不能提交 Git。

## 2. 四个容器怎样通信

```text
浏览器 -> ECS 80/443 -> nginx -> app:8000
                                  |-> postgres:5432
                                  `-> redis:6379
```

- `postgres`、`redis` 只加入 Compose 的 `backend` 网络，不映射 ECS 公网端口。
- 容器内的 `localhost` 只代表当前容器，app 不能用 `localhost` 访问数据库或 Redis。
- PostgreSQL 数据保存到 `PG_DATA_PATH`，Redis AOF 保存到 `REDIS_DATA_PATH`，用户上传文件保存到
  `MEDIA_HOST_PATH`；删除容器不会删除这些 bind mount 目录。
- `app/static` 随 Dockerfile 打进镜像。不要把宿主机 `data/static` 挂载到 `/app/app/static`，否则会遮住新 CSS、Logo 和 favicon。

## 3. 首次部署命令（正式域名 + HTTPS）

先确认文件和目录，不要把密码打印到终端或日志：

```bash
cd /opt/fastapi-blog/current
export COMPOSE_FILE=compose.production.yaml
export COMPOSE_ENV=/opt/fastapi-blog/config/compose-prod.env
export COMPOSE_PROJECT_NAME=fastapi-blog-prod
export APP_IMAGE_TAG=$(git rev-parse --short HEAD)

test -r "$COMPOSE_ENV"
test -r /opt/fastapi-blog/config/app.env
test -r /opt/fastapi-blog/secrets/tls/fullchain.pem
test -r /opt/fastapi-blog/secrets/tls/privkey.key

dc() { docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" "$@"; }
dc config -q
dc build --pull app
dc up -d postgres redis
dc ps postgres redis
dc logs --tail=100 postgres redis
```

上面 `config -q` 只检查 YAML 和变量插值；`build` 会把当前提交的静态文件写入新镜像；
`up -d postgres redis` 首先创建数据依赖并等待健康检查。确认备份和迁移内容后，再执行数据库写操作：

```bash
dc run --rm app uv run --no-sync alembic current
dc run --rm app uv run --no-sync alembic heads
# 确认目标数据库、备份和待执行 revision 后才运行：
dc run --rm app uv run --no-sync alembic upgrade head
dc up -d app nginx
dc ps
dc logs --tail=100 app nginx postgres redis
```

预期四个服务都是 `running`，其中 `postgres`、`redis`、`app` 应为 `healthy`（Nginx 没有 healthcheck）。

## 4. 日常发布

```bash
cd /opt/fastapi-blog/current
git fetch --tags --prune
git checkout <已在测试环境验证的提交或标签>
export COMPOSE_FILE=compose.production.yaml
export COMPOSE_ENV=/opt/fastapi-blog/config/compose-prod.env
export COMPOSE_PROJECT_NAME=fastapi-blog-prod
export APP_IMAGE_TAG=$(git rev-parse --short HEAD)
dc() { docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" "$@"; }

dc config -q
dc build --pull app
dc run --rm app uv run --no-sync alembic current
# 有新的 migration 时，备份并审查后执行一次：
dc run --rm app uv run --no-sync alembic upgrade head
dc up -d --remove-orphans
dc ps
```

只执行 `up -d` 不会把工作树中修改的 CSS、图片或 Python 代码写入旧镜像；修改后必须重新 `build`。
应用镜像回滚不等于数据库回滚，破坏性 `downgrade` 必须另行评审，日常不要执行。

## 5. 环境变量检查与安全操作

```bash
# 只检查名称和值是否存在，不输出值
for key in ENV ALLOWED_HOSTS SECRET_KEY AUTH_COOKIE_SECURE; do
  if grep -q "^${key}=" /opt/fastapi-blog/config/app.env; then echo "$key: present"; else echo "$key: MISSING"; fi
done
for key in APP_DOMAIN APP_IMAGE_TAG APP_ENV_FILE POSTGRES_USER POSTGRES_DB POSTGRES_PASSWORD REDIS_PASSWORD; do
  if grep -q "^${key}=" "$COMPOSE_ENV"; then echo "$key: present"; else echo "$key: MISSING"; fi
done
```

文件建议为 `root:docker`、权限 `640`；如果只有 root 执行 Compose，可改为 `600`。不要使用
`cat app.env`、`printenv`、`docker inspect` 全量输出，因为会泄露 JWT Secret、邮箱授权码或密码。

如果修改 PostgreSQL 密码：

1. 先进入数据库执行 `ALTER ROLE` 修改真实账号密码；
2. 再更新 `compose-prod.env` 的 `POSTGRES_PASSWORD`；
3. `dc up -d app` 让 Compose 重新生成 `DATABASE_URL`。

仅修改环境变量不会改变已经初始化的数据目录中的 PostgreSQL 账号密码。Redis 密码同理，修改后需要
重建/重启 Redis 并确认 app 的 `REDIS_URL` 已同步。

## 6. 备份、恢复与危险命令

逻辑备份示例（输出文件应保存到 ECS 之外）：

```bash
dc exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB"' > /secure-backup/blog-$(date +%F).sql
dc exec -T redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli BGSAVE'
```

Redis 的 Refresh Session、验证码和 OAuth state 属于可重建状态，丢失后用户需要重新登录；PostgreSQL
和 `data/media` 是必须可恢复的业务数据。至少每季度在隔离目录做一次恢复演练。

以下命令可能删除数据或造成长时间中断，生产环境禁止随意执行：

- `docker compose down -v`、`docker system prune -a --volumes`；
- `alembic downgrade`、`pg_restore --clean`、手工 `DROP`；
- 未确认归属就停止宿主机 Nginx、Docker 或通过 PID `kill` 进程。

## 7. 故障排查顺序

```bash
dc ps
dc logs --tail=200 postgres redis app nginx
dc exec app sh -c 'test -f /app/app/static/images/logo.png && test -f /app/app/static/images/favicon.ico'
curl -fsS -H "Host: $APP_DOMAIN" http://127.0.0.1:8000/health/live
curl -fsS -H "Host: $APP_DOMAIN" http://127.0.0.1:8000/health/ready
```

按以下边界定位：

1. `postgres` 不健康：检查数据目录属主（`postgres:16-alpine` 默认 UID 70）、磁盘空间和日志。
2. `redis` 不健康：检查 Redis 目录属主（`redis:7-alpine` 默认 UID 999）、密码和 AOF 文件。
3. `app` 不健康：读取最后一个 DBAPI/Redis 异常，确认 Compose 注入的主机是 `postgres`/`redis`。
4. Nginx 502：确认 app healthy、Nginx `proxy_pass` 服务名和 80/443 端口占用。
5. 样式或图片旧：确认执行了 `dc build --pull app`，且没有挂载 `data/static` 覆盖镜像目录。

## 8. 无域名公网 IP 临时模式（历史验收用途）

没有域名或证书时只能使用 `compose.public-ip.yaml`，并设置 `PUBLIC_IP_MODE=true`、
`AUTH_COOKIE_SECURE=false`。这是明文 HTTP 内测模式，不能与正式 HTTPS Compose 同时占用 80/443，
也不能据此修改正式 `app.env`。备案和证书就绪后，停止临时项目并按本文第 3 节切换。

## 9. RDS/Tair 的未来迁移边界

未来若预算允许迁移到 RDS/Tair：先备份并导入 PostgreSQL，评估 Redis 会话丢失，再停止本机
`postgres`/`redis` 写入，最后修改连接串并验证。不能让本机数据库和 RDS 同时接收同一套生产流量，
也不能只改地址而不迁移数据。

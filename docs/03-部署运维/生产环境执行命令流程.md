# 生产环境执行命令流程

本手册针对当前仓库的正式域名 HTTPS 单机部署：ECS 运行 FastAPI、Nginx、PostgreSQL 和 Redis
四个 Docker 容器。PostgreSQL 与 Redis 使用 ECS 宿主机目录持久化，不需要购买 RDS/Tair。命令默认
在 ECS 的 Bash 中执行，不能直接复制到 Windows PowerShell。

> 重要边界：
>
> - `/opt/fastapi-blog/config/compose-prod.env` 是 Docker Compose 专用配置，保存域名、镜像标签、
>   PostgreSQL/Redis 容器账号密码和宿主机数据目录；建议 root:docker + 权限 640（仅 root 执行 Compose 时可用 600）。
> - `/opt/fastapi-blog/config/app.env` 是 FastAPI 运行时配置，由 Compose 的 `services.app.env_file`
>   注入 `app` 容器，保存 `postgres`/`redis` 服务名、JWT、Cookie、邮件等配置。
> - `compose.production.yaml` 启动 `app`、`nginx`、`postgres`、`redis` 四个服务；数据库和 Redis
>   只在 Compose `backend` 网络可见，不映射公网端口。
> - `app/static` 随 Docker 镜像发布，不要创建或挂载 `/opt/fastapi-blog/data/static`，否则旧 CSS、Logo
>   或 favicon 会覆盖镜像中的新版本。

首次采用单机 Docker 方案，建议先阅读[《Docker 本机 PostgreSQL 与 Redis 正式部署教程》](运维教程/08-Docker本机PostgreSQL与Redis正式部署.md)。
本文件是已经完成目录和配置准备后的命令级发布 Runbook。

## 0. 先分清每个服务由谁启动

正式域名方案中，各组件的启动位置如下：

| 组件 | 正式运行位置 | 谁负责启动 | `docker compose ps` 是否出现 |
|---|---|---|---|
| FastAPI `app` | ECS Docker 容器 | ECS 上的 Compose | 是 |
| Nginx | ECS Docker 容器 | ECS 上的 Compose | 是 |
| PostgreSQL | ECS Docker `postgres` 容器 | ECS 上的 Compose | 是 |
| Redis | ECS Docker `redis` 容器 | ECS 上的 Compose | 是 |
| 用户上传媒体 | ECS `/opt/fastapi-blog/data/media` | 宿主机目录 + Compose 挂载 | 作为 `app` 的挂载出现 |
| TLS 证书 | ECS `/opt/fastapi-blog/secrets/tls` | 宿主机文件 + Nginx 只读挂载 | 作为 `nginx` 的挂载出现 |

Redis 容器保存 Refresh Session、密码重置验证码和 QQ 登录 OAuth `state` 等短期状态。应用通过
Compose 内部 DNS 使用 `redis:6379`，数据库通过 `postgres:5432` 连接；两个服务均不允许公网访问。

当前正式方案直接由 `compose.production.yaml` 创建四个容器：

```bash
docker compose \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml \
  up -d --build
```

该命令会创建 `app`、`nginx`、`postgres` 和 `redis`，并使用 compose-prod.env 中的数据目录和密码。
旧的 `compose.public-ip.local-services.yaml` 仅为历史临时方案保留，不要与正式 Compose 叠加。

## 1. 首次部署前的目录和文件

ECS 目录应当类似：

```text
/opt/fastapi-blog/
├── current/                 # 已测试的 Git 工作树
├── config/
│   ├── compose-prod.env     # Compose 参数和数据库/Redis 密码，权限 640 root:docker
│   └── app.env              # FastAPI 生产配置，权限 640 root:docker（包含 Secret）
├── data/postgres/           # PostgreSQL 数据目录
├── data/redis/              # Redis AOF 数据目录
├── data/media/              # 用户上传文件，持久化挂载
└── secrets/tls/
    ├── fullchain.pem        # 证书链
    └── privkey.key          # 私钥；当前 Nginx 模板使用 .key 后缀
```

创建目录并设置媒体目录权限：

```bash
sudo install -d -m 750 /opt/fastapi-blog/config
sudo install -d -o 70 -g 70 -m 700 /opt/fastapi-blog/data/postgres
sudo install -d -o 999 -g 1000 -m 700 /opt/fastapi-blog/data/redis
sudo install -d -o 10001 -g 10001 -m 750 /opt/fastapi-blog/data/media
sudo install -d -m 750 /opt/fastapi-blog/secrets/tls
```

应用容器以 UID `10001` 运行。媒体目录必须让该 UID 可写，不能为了省事使用 `777`。

## 2. 安装两个生产配置文件

仓库中的 [deploy/compose-prod.env.example](../../deploy/compose-prod.env.example) 是字段模板。请先复制为
本地未提交的 `deploy/compose-prod.env`，填写密码后再上传到 ECS：

```bash
# 在本地仓库执行
scp deploy/compose-prod.env <ECS用户>@<ECS公网IP>:/tmp/compose-prod.env

# 在 ECS 执行；文件含 PostgreSQL/Redis 密码，建议使用 640 root:docker。
sudo install -o root -g docker -m 640 /tmp/compose-prod.env \
  /opt/fastapi-blog/config/compose-prod.env
```

`compose-prod.env` 中的参数说明：

| 变量 | 当前值/来源 | 用途 |
|---|---|---|
| `APP_DOMAIN` | `www.sanwan.xyz` | 替换 Nginx 模板中的 `server_name`、HTTPS 跳转和 Host |
| `APP_IMAGE_TAG` | `production`（发布时由 Git 短 SHA 覆盖） | 生成 `fastapi-blog:<标签>` 镜像 |
| `APP_ENV_FILE` | `/opt/fastapi-blog/config/app.env` | 指定注入 FastAPI 容器的运行时配置 |
| `MEDIA_HOST_PATH` | `/opt/fastapi-blog/data/media` | 持久化用户上传文件 |
| `TLS_HOST_PATH` | `/opt/fastapi-blog/secrets/tls` | 只读挂载证书和私钥目录 |
| `COMPOSE_PROJECT_NAME` | `fastapi-blog-prod` | 固定容器、网络和命名，避免不同目录产生重复项目 |
| `POSTGRES_USER` / `POSTGRES_DB` | `fastapi_blog` / `fastapi_blog_postgresql` | 首次初始化本机 PostgreSQL；Compose 同时用它生成 app 连接串 |
| `POSTGRES_PASSWORD` | ECS 上填写的随机值 | PostgreSQL 容器首次初始化密码；Compose 同时注入 `DATABASE_URL` |
| `REDIS_PASSWORD` | ECS 上填写的随机值 | Redis 容器认证密码；Compose 同时注入 `REDIS_URL` |
| `PG_DATA_PATH` / `REDIS_DATA_PATH` | `/opt/fastapi-blog/data/{postgres,redis}` | 持久化数据库和 Redis 数据，建议位于独立数据盘 |

创建或编辑应用配置：

```bash
sudo touch /opt/fastapi-blog/config/app.env
sudo chown root:docker /opt/fastapi-blog/config/app.env
sudo chmod 640 /opt/fastapi-blog/config/app.env
sudoedit /opt/fastapi-blog/config/app.env
```

`app.env` 至少应包含以下结构，尖括号内容必须替换成真实值；不要把真实值提交到 Git：

```dotenv
ENV=production
PROJECT_TITLE=三碗博客
ALLOWED_HOSTS=["www.sanwan.xyz"]
AUTH_COOKIE_SECURE=true
PUBLIC_IP_MODE=false

# DATABASE_URL/REDIS_URL 由 compose.production.yaml 根据 compose-prod.env 自动生成；不要在 app.env 重复填写。
REDIS_KEY_PREFIX=fastapi-blog:production
REDIS_SOCKET_TIMEOUT_SECONDS=2

SECRET_KEY=<至少32个字符的随机字符串>
ACCESS_TOKEN_EXPIRE_MINUTES=30
REFRESH_TOKEN_EXPIRE_MINUTES=10080
REFRESH_IDLE_TIMEOUT_MINUTES=1440

LOG_LEVEL=INFO
LOG_FORMAT=json
LOG_TO_FILE=false
```

Compose 密码建议只使用字母、数字、点、短横线和下划线，避免连接串 URL 编码问题。不要把根目录 `.env`
直接当作生产配置；生产以 `/opt/fastapi-blog/config/app.env` 和 `compose-prod.env` 为准。

证书文件名必须与当前 Nginx 模板一致：

```bash
# 阿里云下载的 www.sanwan.xyz.pem 通常是证书链文件
sudo install -o root -g root -m 644 www.sanwan.xyz.pem \
  /opt/fastapi-blog/secrets/tls/fullchain.pem
# 阿里云下载的 www.sanwan.xyz.key 是私钥
sudo install -o root -g root -m 640 www.sanwan.xyz.key \
  /opt/fastapi-blog/secrets/tls/privkey.key
```

不要执行 `cat privkey.key`，也不要把私钥内容粘贴到聊天、工单或日志中。

## 3. 每次发布都先固定版本和 Compose 参数

以下变量只在当前 SSH/Bash 会话有效；重新登录 ECS 后必须重新执行。`APP_IMAGE_TAG` 使用当前已测试
提交的短 SHA，Shell 变量优先级高于 `compose-prod.env` 中的 `production` 默认值。

```bash
cd /opt/fastapi-blog/current
git fetch --all --prune
git checkout <已经在测试环境验证过的提交或标签>
git status --short

export COMPOSE_FILE=compose.production.yaml
export COMPOSE_ENV=/opt/fastapi-blog/config/compose-prod.env
export APP_DOMAIN=www.sanwan.xyz  # 仅供 curl/openssl 验收使用；必须与 compose-prod.env 一致
export APP_IMAGE_TAG=$(git rev-parse --short HEAD)
export COMPOSE_PROJECT_NAME=fastapi-blog-prod

test -r "$COMPOSE_ENV"
test -r /opt/fastapi-blog/config/app.env
```

预期 `git status --short` 没有未提交修改。生产服务器不要直接对未知分支执行 `git pull` 后上线。

为避免每条命令重复书写参数，可以在当前 shell 定义辅助函数：

```bash
dc() {
  docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" "$@"
}
```

`dc` 只对当前 shell 有效，不会修改 Docker 或项目文件。

## 4. 发布前配置检查（只读）

### 4.1 检查配置文件存在且不打印 Secret

```bash
for key in ENV ALLOWED_HOSTS AUTH_COOKIE_SECURE PUBLIC_IP_MODE; do
  if grep -q "^${key}=" /opt/fastapi-blog/config/app.env; then
    echo "$key=set"
  else
    echo "$key=missing"
  fi
done

for key in SECRET_KEY; do
  if grep -q "^${key}=" /opt/fastapi-blog/config/app.env; then
    echo "$key=set"
  else
    echo "$key=missing"
  fi
done

for key in POSTGRES_USER POSTGRES_DB POSTGRES_PASSWORD REDIS_PASSWORD APP_DOMAIN APP_ENV_FILE; do
  if grep -q "^${key}=" "$COMPOSE_ENV"; then
    echo "$key=set"
  else
    echo "$key=missing"
  fi
done
```

这两个循环只输出变量名和 `set/missing`，不会输出连接串、密码或密钥。生产预期至少是：
`ENV=production`、`ALLOWED_HOSTS=["www.sanwan.xyz"]`、`AUTH_COOKIE_SECURE=true`、
`PUBLIC_IP_MODE=false`。

### 4.2 检查 Compose 展开和 Nginx 配置

```bash
# -q 表示 quiet，只做 YAML 和变量解析，不把展开配置打印到终端。
dc config -q

# 只启动一次性 Nginx 检查容器，不依赖 app，也不改变生产数据。
dc run --rm --no-deps nginx nginx -t
```

`dc config -q` 只能证明 Compose 文件和变量可解析；它不会验证 PostgreSQL/Redis 网络、证书内容或应用健康。
不要把不带 `-q` 的 `dc config` 输出复制到聊天或工单。

### 4.3 检查媒体目录和证书

```bash
test -d /opt/fastapi-blog/data/media
test -r /opt/fastapi-blog/secrets/tls/fullchain.pem
test -r /opt/fastapi-blog/secrets/tls/privkey.key
```

证书文件存在不代表域名 SAN 正确，后续 HTTPS 验收还要检查证书。

## 5. 构建应用镜像

```bash
dc build --pull app
docker image inspect "fastapi-blog:$APP_IMAGE_TAG" \
  --format 'image={{.Id}} created={{.Created}}'
```

`build` 根据 Dockerfile 生成应用镜像，不会启动服务或修改数据库；`--pull` 会尝试更新基础镜像，
需要 ECS 能访问镜像仓库；`app` 表示只构建 FastAPI 服务。Dockerfile 的 `COPY app ./app` 会将
模板、CSS、JavaScript、Logo 和 favicon 一起写入镜像。因此每次代码或静态资源更新后都必须重新
`build`，只执行 `up -d` 可能继续使用旧镜像。

镜像构建阶段已经执行 `uv sync --frozen --no-dev`，依赖版本由提交进仓库的 `uv.lock` 固定。
生产容器的启动命令和运维命令统一使用 `uv run --no-sync`：它只使用镜像内已经存在的虚拟环境，
不会在每次容器启动时再次解析或修改依赖。健康检查直接调用 `/app/.venv/bin/python`，因此也不会
因为 `uv` 同步卡住而把正常运行的 app 判定为 `unhealthy`。如果以后新增依赖，仍需先更新并提交
`uv.lock`，重新构建镜像；不能靠去掉 `--no-sync` 在生产运行时临时安装依赖。

## 6. Alembic 迁移闸门

迁移会写入本机 PostgreSQL，必须先完成数据目录/逻辑备份并记录发布信息。首次部署或有数据库结构变更时，先执行只读检查：

```bash
# 只读取镜像中的迁移链，不连接数据库。
dc run --rm app uv run --no-sync alembic heads
dc run --rm app uv run --no-sync alembic history

# 读取本机 PostgreSQL 当前 revision；会连接数据库，但不修改结构。
dc run --rm app uv run --no-sync alembic current
```

`heads` 应只有一个目标 head。若出现多个 head、数据库名称不确定、连接到错误实例或 migration
内容与预期不符，应立即停止，不要用 `stamp head` 掩盖问题。

确认 PostgreSQL 备份已完成、数据目录和数据库名称无误后，才执行写操作：

```bash
dc run --rm app uv run --no-sync alembic upgrade head
dc run --rm app uv run --no-sync alembic current
dc run --rm app uv run --no-sync alembic heads
```

`run --rm` 创建一次性容器，命令结束后删除该容器，不会删除镜像、媒体目录或 PostgreSQL 数据目录。未经明确
授权不要执行 `alembic downgrade`、手工删表或 `docker compose down -v`。

## 7. 启动或更新服务

```bash
dc up -d --force-recreate --remove-orphans
dc ps
dc logs --tail=100 app nginx postgres redis
```

`up -d` 在后台创建或更新四个服务；`--force-recreate` 确保新镜像和最新 Nginx 模板生效；`ps` 预期
显示 `postgres`、`redis`、`app` 为 `healthy`、`nginx` 为 `running`；`logs` 用于查看启动异常，重点
关注 app 日志中最后一个 PostgreSQL/Redis 异常。Nginx 依赖 app 健康检查，readiness 失败时不要用重启循环掩盖问题。

## 8. 启动后验收

### 8.1 容器内健康检查

```bash
dc exec app uv run --no-sync python -c \
  "import json,os,urllib.request; h=json.loads(os.environ['ALLOWED_HOSTS'])[0]; r=urllib.request.Request('http://127.0.0.1:8000/health/ready',headers={'Host':h}); print(urllib.request.urlopen(r,timeout=3).read().decode())"
```

预期输出：`{"status":"ready"}`。

### 8.2 HTTPS 和域名检查

DNS 已指向 ECS 公网 IP 后执行：

```bash
curl -fsSI "https://www.sanwan.xyz/"
curl -fsS "https://www.sanwan.xyz/health/live"
curl -fsS "https://www.sanwan.xyz/health/ready"
```

DNS 尚未切换时，可在 ECS 本机用 `--resolve` 验证 Nginx、证书和 Host：

```bash
curl -I --resolve www.sanwan.xyz:80:127.0.0.1 http://www.sanwan.xyz/
curl -fsS --resolve www.sanwan.xyz:443:127.0.0.1 https://www.sanwan.xyz/health/live
```

预期 HTTP 返回 301，HTTPS/live/ready 返回 200。不要使用 `curl -k` 忽略证书错误完成正式验收。

### 8.3 静态文件和媒体持久化检查

```bash
dc exec app sh -c \
  'test -f /app/app/static/css/site.css && \
   test -f /app/app/static/images/logo.png && \
   test -f /app/app/static/images/favicon.ico'

curl -fsSI https://www.sanwan.xyz/static/css/site.css
curl -fsSI https://www.sanwan.xyz/static/images/logo.png
curl -fsSI https://www.sanwan.xyz/static/images/favicon.ico

# 确认 media 是宿主机挂载，并做一次可恢复的写入测试。
dc exec app sh -c \
  'mount | grep "/app/app/media" && touch /app/app/media/.write-test && rm /app/app/media/.write-test'
```

静态文件检查失败时，先确认执行了 `dc build --pull app` 且运行容器来自当前镜像；不要手工把文件
复制到 `data/static`。媒体写入失败时，检查宿主目录权限和容器 UID `10001`。

## 9. 创建生产管理员（首次部署一次）

这是数据库写操作，必须确认当前连接的是目标本机 PostgreSQL 数据目录：

```bash
dc run --rm app uv run --no-sync python -m app.cli create-admin
```

`run --rm` 每次都会创建并删除一个一次性容器，所以比进入已运行容器慢；现在命令中的
`--no-sync` 已经跳过运行时依赖同步。若 `app` 已经是 `healthy`，优先使用 `exec`，并继续通过
前面定义的 `dc` 函数加载同一份 Compose 参数：

```bash
dc exec app uv run --no-sync python -m app.cli create-admin
```

如果 `app` 尚未启动，或需要与运行容器隔离，再使用 `run --rm`：

```bash
dc run --rm app uv run --no-sync python -m app.cli create-admin
```


命令会交互输入密码，密码不会出现在命令参数中。不要用 SQL 手工把普通用户改成管理员。

## 10. 日常发布流程

以后每次代码更新重复以下步骤：

```bash
cd /opt/fastapi-blog/current
git fetch --all --prune
git checkout <新的已测试提交或标签>
git status --short

export COMPOSE_FILE=compose.production.yaml
export COMPOSE_ENV=/opt/fastapi-blog/config/compose-prod.env
export APP_IMAGE_TAG=$(git rev-parse --short HEAD)
export COMPOSE_PROJECT_NAME=fastapi-blog-prod
dc() { docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" "$@"; }

dc config -q
dc build --pull app
dc run --rm app uv run --no-sync alembic heads
dc run --rm app uv run --no-sync alembic current

# 确认备份和迁移审查后
dc run --rm app uv run --no-sync alembic upgrade head
dc up -d --force-recreate --remove-orphans
dc ps
dc logs --tail=100 app nginx
```

如果本次只修改了 Nginx 模板或证书，也要重新创建 Nginx：

```bash
dc run --rm --no-deps nginx nginx -t
dc up -d --force-recreate nginx
dc exec nginx nginx -t
```

## 11. 回滚原则

### 11.1 应用代码回滚

应用回滚应切换到上一个已验证的 Git 提交，然后重新构建和启动：

```bash
git checkout <上一个可运行的提交或标签>
export APP_IMAGE_TAG=$(git rev-parse --short HEAD)
dc build --pull app
dc up -d --force-recreate app nginx
dc ps
```

### 11.2 数据库回滚

应用镜像回滚不等于数据库回滚。若新版本已经执行了不可逆迁移：

1. 先停止继续发布并保留日志、当前 revision 和备份记录；
2. 判断旧代码是否能兼容当前数据库结构；
3. 只有经过审查并明确授权，才设计恢复或向下迁移方案。

不要为了“让服务启动”直接执行 `alembic stamp head`、破坏性 `downgrade`、DROP 表或删除 Docker
Volume。

## 12. 常用运维命令与含义

```bash
dc ps                          # 查看 app/nginx 状态
dc logs --tail=200 app nginx   # 查看最近日志
dc logs -f app nginx           # 持续跟踪日志，Ctrl+C 只退出查看
dc restart app                 # 重启 app，不重新构建镜像
dc restart nginx               # 重启 Nginx，使模板替换重新执行
dc stop                        # 停止服务，保留容器、镜像和数据
dc start                       # 启动已经停止的服务
dc exec nginx nginx -t         # 检查运行中 Nginx 配置
dc exec nginx nginx -s reload  # 平滑重载 Nginx
```

`restart` 不会把工作树的新代码写入镜像；代码变化必须先 `build`，再 `up --force-recreate`。
`stop/start` 不会删除数据。除非明确授权，不要使用 `docker compose down -v`，它可能删除本地卷数据。

## 13. 故障排查顺序

| 现象 | 先检查 | 常见原因 |
|---|---|---|
| `Couldn't find env file` | `test -r "$COMPOSE_ENV"` | `--env-file` 路径写错或文件未上传 |
| Compose 提示 `APP_DOMAIN` 缺失 | `dc config -q` | 未使用 `compose-prod.env` 或配置值为空 |
| app `unhealthy` | `dc logs --tail=200 app postgres redis` | 服务状态、账号密码、数据库名、迁移或 `ALLOWED_HOSTS` 错误 |
| Nginx `nginx -t` 失败 | `ls -l /opt/fastapi-blog/secrets/tls` | 证书文件名、权限、域名 SAN 或证书链错误 |
| 502 Bad Gateway | `dc ps`、app 日志、Nginx 日志 | app 未 healthy 或容器网络/端口配置错误 |
| 样式或图片仍是旧版本 | `dc exec app test -f ...`、镜像标签 | 未重新 build，或错误挂载了 `data/static` |
| 上传失败 | `dc exec app id`、media 挂载检查 | UID `10001` 无宿主目录写权限 |
| 迁移报错 | Traceback 最后一个 PostgreSQL/DBAPI 异常 | 目标数据库、权限、revision 或迁移内容不一致 |

排查时不要使用 `env`、`printenv`、`docker inspect` 全量输出配置；只输出状态、变量名或经过脱敏的
错误信息。数据库 URI、Redis 密码、JWT Secret、Cookie 和私钥都不能进入公开日志。

## 14. 一次完整流程的最短版

确认第 1～4 节前置条件完成后，可以使用下面的速查版：

```bash
cd /opt/fastapi-blog/current
git fetch --all --prune
git checkout <已测试提交或标签>
export COMPOSE_FILE=compose.production.yaml
export COMPOSE_ENV=/opt/fastapi-blog/config/compose-prod.env
export APP_IMAGE_TAG=$(git rev-parse --short HEAD)
export COMPOSE_PROJECT_NAME=fastapi-blog-prod
dc() { docker compose --env-file "$COMPOSE_ENV" -f "$COMPOSE_FILE" "$@"; }

test -r "$COMPOSE_ENV"
test -r /opt/fastapi-blog/config/app.env
dc config -q
dc build --pull app
dc run --rm app uv run --no-sync alembic current
# 备份和审查迁移后
dc run --rm app uv run --no-sync alembic upgrade head
dc up -d --force-recreate --remove-orphans
dc ps
dc logs --tail=100 app nginx postgres redis
```

这份速查版仍然不能替代 PostgreSQL/Redis 备份、证书检查和 HTTPS 验收；它只是保证命令顺序一致。

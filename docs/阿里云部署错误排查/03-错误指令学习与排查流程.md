# 阿里云部署故障排查学习流程

本文把“启动项目报错-1.txt”中的处理命令，重新整理成一条安全、可重复的排查链。附件是一次真实操作记录，其中部分命令会删除文件、输出密码、停止系统服务或修改生产数据库；这些命令只能作为“发生了什么”的学习材料，不能原样复制执行。

本文默认：

- 项目目录：/opt/fastapi-blog/current
- Secret 配置：/opt/fastapi-blog/config/app.env
- 正式 Compose：compose.production.yaml
- 无域名临时 Compose：compose.public-ip.yaml
- <ECS_PUBLIC_IP> 等占位符必须替换，不能原样执行。

## 1. 排查总原则

每一步都遵循：

~~~text
确认当前对象
  -> 只读检查
  -> 根据错误边界判断
  -> 最小范围修复
  -> 再次验证
~~~

不要一开始就执行 docker compose up -d --build。如果路径、配置、端口、数据库和 Redis 没有确认，启动命令只会把多个问题混在一起。

高风险操作包括：

- rm -rf：删除目录，不可逆；
- cat app.env：可能把密码、数据库 URI、Redis URI、JWT Secret 输出到终端；
- systemctl restart docker：影响宿主机所有 Docker 服务；
- systemctl stop/disable nginx：改变宿主机服务状态；
- kill PID：可能误杀无关进程；
- alembic upgrade head：修改数据库结构；
- docker compose down -v：可能删除数据卷，生产环境禁止随意执行。

## 2. 第一阶段：确认服务器目录

### 2.1 确认当前目录

原记录使用：

~~~bash
cd /opt/fastapi-blog/current && pwd && ls -la
~~~

推荐增加 Git 根目录检查：

~~~bash
cd /opt/fastapi-blog/current
pwd
git rev-parse --show-toplevel
git status --short
git rev-parse --short HEAD
~~~

学习重点：

- pwd：我现在在哪个目录？
- git rev-parse --show-toplevel：这里是不是目标仓库？
- git status --short：服务器源码是否被手工修改？
- git rev-parse --short HEAD：当前运行的代码版本是什么？

### 2.2 不要直接删除可疑目录

原记录出现过：

~~~bash
rm -rf /home/admin/fastapi-blog
~~~

这条命令会递归删除目录，和当前项目目录 /opt/fastapi-blog/current 也不是同一个路径。它不能解决 Docker、DNS、数据库或 Nginx 问题。

安全替代方式是先只读确认：

~~~bash
ls -ld /home/admin/fastapi-blog
ls -la /home/admin/fastapi-blog/.git/HEAD 2>/dev/null
~~~

只有明确确认目录、用途、备份和删除授权后，才考虑删除。正常部署排错不需要这条命令。

## 3. 第二阶段：检查配置，但不要泄露 Secret

### 3.1 查找配置和证书文件

原记录使用 find、ls：

~~~bash
cd /opt/fastapi-blog/current
find . -maxdepth 2 \( -name '*.env*' -o -name '*.yaml' -o -name '*.yml' \) -print
find /opt/fastapi-blog -type f \( -name '*.pem' -o -name '*.crt' -o -name '*.key' \) -print
ls -la /opt/fastapi-blog/config
ls -la /opt/fastapi-blog/secrets/tls
~~~

这些命令只显示文件名和权限，不应该显示证书私钥内容。

### 3.2 不要使用 cat app.env

原记录使用：

~~~bash
cat /opt/fastapi-blog/config/app.env
~~~

这会把完整密码和连接 URI 输出到终端。安全检查只看变量名：

~~~bash
grep -E '^[A-Z][A-Z0-9_]*=' /opt/fastapi-blog/config/app.env \
  | cut -d= -f1 | sort -u
~~~

如果需要确认变量是否存在而不显示值：

~~~bash
for key in ENV ALLOWED_HOSTS DATABASE_URL SECRET_KEY AUTH_COOKIE_SECURE REDIS_URL; do
  if grep -q "^$key=" /opt/fastapi-blog/config/app.env; then
    echo "$key: present"
  else
    echo "$key: missing"
  fi
done
~~~

不要用 tail app.env 或 grep SECRET_KEY app.env 直接把密钥值打印出来。

### 3.3 检查应用到底要求哪些配置

原记录使用：

~~~bash
grep -r 'SECRET_KEY\|ALLOWED_HOSTS\|APP_DOMAIN' app/ --include='*.py'
cat app/core/config.py
~~~

学习目的：

- 从 Settings 找到必填变量；
- 从校验器确认组合要求；
- 确认生产环境是否强制 PostgreSQL、Redis 和 Secure Cookie；
- 确认 ALLOWED_HOSTS 是否只允许域名或公网 IP。

当前项目的关键组合：

- 正式域名 HTTPS：AUTH_COOKIE_SECURE=true；
- 无域名临时 HTTP：PUBLIC_IP_MODE=true、AUTH_COOKIE_SECURE=false、ALLOWED_HOSTS 只能是 IPv4；
- 生产数据库必须使用 PostgreSQL；
- Redis 不能指向生产环境的 localhost。

## 4. 第三阶段：区分公网 IP、私有 IP 和服务地址

获取 ECS 私有地址：

~~~bash
ip addr
hostname -I
~~~

获取公网出口地址：

~~~bash
curl -s --max-time 5 ifconfig.me
~~~

注意：

- ECS 公网 IP/EIP 用于浏览器访问 Nginx；
- ECS 私有 IP 用于 VPC 内部通信；
- RDS/Tair 的内网连接地址不是 ECS 的 IP；
- 本机 Docker 依赖使用服务名 postgres、redis；
- 不能把 localhost 当作其他容器的地址。

## 5. 第四阶段：先验证 Compose 能否解析

正式域名模式：

~~~bash
cd /opt/fastapi-blog/current
export APP_DOMAIN=<APP_DOMAIN>
export APP_ENV_FILE=/opt/fastapi-blog/config/app.env
export MEDIA_HOST_PATH=/opt/fastapi-blog/data/media
export TLS_HOST_PATH=/opt/fastapi-blog/secrets/tls

docker compose -p fastapi-blog-prod -f compose.production.yaml config -q
~~~

公网 IP 模式：

~~~bash
export APP_PUBLIC_IP=<ECS_PUBLIC_IP>
export APP_ENV_FILE=/opt/fastapi-blog/config/app-ip.env
export MEDIA_HOST_PATH=/opt/fastapi-blog/data/media

docker compose -p fastapi-blog-ip -f compose.public-ip.yaml config -q
~~~

config -q 只检查 YAML 和变量展开，不会启动容器，也不会连接数据库。

如果报 required variable APP_DOMAIN is missing，说明 Compose 变量没有传入。app.env 里的变量不一定会被 Compose 用于解析服务定义，应该使用 --env-file 或当前 Shell 的环境变量。

## 6. 第五阶段：Docker 构建 DNS 排查

附件中的错误是：

~~~text
uv sync ... dns error: failed to lookup address information
~~~

这说明构建容器无法解析 Python 包站点，不等于 FastAPI 代码错误。

### 6.1 先检查宿主机

~~~bash
getent hosts pypi.org files.pythonhosted.org
curl -I --connect-timeout 5 https://pypi.org/simple/fastapi/
cat /etc/resolv.conf
~~~

### 6.2 再检查容器网络

~~~bash
docker run --rm python:3.13-slim python -c \
  "import socket; print(socket.gethostbyname('files.pythonhosted.org'))"

docker run --rm python:3.13-slim python -c \
  "import urllib.request; print(urllib.request.urlopen('https://files.pythonhosted.org', timeout=10).status)"
~~~

判断方法：

| 宿主机 | 容器 | 结论 |
|---|---|---|
| 失败 | 失败 | ECS 出口、DNS 或安全组整体有问题 |
| 成功 | 失败 | Docker daemon/BuildKit 网络配置有问题 |
| 成功 | 成功 | DNS 基本正常，应继续检查包索引、代理或依赖版本 |

### 6.3 检查 Docker daemon 配置

原记录使用：

~~~bash
cat /etc/docker/daemon.json
~~~

只读查看可以保留。不要直接覆盖整个文件：

~~~bash
sudo cp /etc/docker/daemon.json \
  "/etc/docker/daemon.json.bak.$(date +%Y%m%d%H%M%S)" 2>/dev/null || true
sudo python3 -m json.tool /etc/docker/daemon.json
~~~

如果确实需要增加 DNS，应先用 sudoedit /etc/docker/daemon.json 合并现有 JSON，不能盲目抄写并删除已有 registry-mirrors、代理或其他配置。修改后：

~~~bash
sudo python3 -m json.tool /etc/docker/daemon.json
sudo systemctl restart docker
sudo systemctl is-active docker
docker ps
~~~

重启 Docker 会影响宿主机上的所有容器，应安排维护窗口。

### 6.4 临时使用 PyPI 镜像

当前仓库支持可选构建参数：

~~~bash
UV_INDEX_URL=https://mirrors.aliyun.com/pypi/simple \
docker compose -p fastapi-blog-ip -f compose.public-ip.yaml build --pull app
~~~

这只改变 Python 包下载地址，不等于修复 Docker DNS。构建成功后仍应确认网络根因。

## 7. 第六阶段：启动并查看容器

启动前先确认选择了正确配置：

~~~bash
# 无域名
docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml up -d --build

# 备案后域名
docker compose -p fastapi-blog-prod \
  --env-file /opt/fastapi-blog/config/compose-prod.env \
  -f compose.production.yaml up -d --build
~~~

查看状态：

~~~bash
docker compose -p fastapi-blog-ip -f compose.public-ip.yaml ps
docker compose -p fastapi-blog-ip -f compose.public-ip.yaml logs --tail=100 app nginx
~~~

学习重点：

- up -d：后台启动；
- --build：先重新构建镜像；
- ps：看容器是否运行、健康状态和端口；
- logs：看应用启动异常、数据库连接异常和 Nginx 错误。

不要只看 Nginx 日志。app 的最后一个 PostgreSQL/Redis 异常通常才是根因。

## 8. 第七阶段：理解并验证健康检查

代码接口：

~~~bash
curl -i -H 'Host: <ECS_PUBLIC_IP>' \
  http://127.0.0.1/health/live

curl -i -H 'Host: <ECS_PUBLIC_IP>' \
  http://127.0.0.1/health/ready
~~~

容器内手工验证必须使用正确 Host：

~~~bash
docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml exec app \
  python -c "import json,os,urllib.request; h=json.loads(os.environ['ALLOWED_HOSTS'])[0]; r=urllib.request.Request('http://127.0.0.1:8000/health/ready',headers={'Host':h}); print(urllib.request.urlopen(r,timeout=3).read().decode())"
~~~

查看 Docker 保存的探针结果：

~~~bash
APP_CONTAINER=$(docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml ps -q app)

docker inspect --format '{{json .State.Health}}' "$APP_CONTAINER"
~~~

常见判断：

- live=200、ready=503：FastAPI 进程活着，但数据库或 Redis 不可用；
- Invalid host header：探针请求的 Host 不在 ALLOWED_HOSTS；
- app healthy、Nginx 未启动：检查 Nginx 端口、证书和 Nginx 配置；
- app unhealthy：Nginx 的 depends_on 不会继续启动。

## 9. 第八阶段：排查数据库和 Redis

### 9.1 先看是否有服务监听

~~~bash
sudo ss -lntp | grep -E ':(5432|6379)\b' || true
docker ps -a --format '{{.Names}}\t{{.Status}}\t{{.Ports}}'
systemctl list-units --type=service --all \
  | grep -iE 'postgres|redis' || true
~~~

如果 RDS/Tair 是托管服务，宿主机没有 5432/6379 监听是正常的；应测试 ECS 到它们的私网地址，而不是要求本机出现进程。

### 9.2 测试网络端口

~~~bash
nc -vz <RDS_PRIVATE_HOST> 5432
nc -vz <TAIR_PRIVATE_HOST> 6379
~~~

结果解释：

- succeeded：网络路径和端口基本可达，继续检查用户名、密码、数据库名或 TLS；
- Connection refused：目标主机可达，但端口没有服务监听或被主动拒绝；
- timed out：安全组、白名单、路由或网络 ACL 可能阻断；
- Name or service not known：主机名解析失败。

本机 Docker 依赖则检查 Compose 服务名：

~~~bash
docker compose -p fastapi-blog-ip \
  -f compose.public-ip.yaml \
  -f compose.public-ip.local-services.yaml exec app \
  getent hosts postgres redis
~~~

### 9.3 不要把本机 IP 和服务名混用

- RDS/Tair：使用托管服务的 VPC 内网地址；
- 本机 Docker：使用 postgres、redis；
- app 容器内的 localhost：只代表 app 自己。

## 10. 第九阶段：处理宿主机 80 端口冲突

原记录发现宿主机 Nginx 已占用 80，Docker Nginx 无法绑定。

先只读检查：

~~~bash
sudo ss -lntp | grep ':80\b'
sudo lsof -nP -iTCP:80 -sTCP:LISTEN
sudo systemctl status nginx --no-pager
~~~

确认确实是独立宿主机 Nginx 后，才执行：

~~~bash
sudo systemctl stop nginx
sudo ss -lntp | grep ':80\b' || true
~~~

是否执行 disable 要根据你的运维选择决定：

~~~bash
sudo systemctl disable nginx
~~~

它会改变服务器重启后的行为，不是临时释放端口的必要命令。

不要直接复制日志中的 kill 45231。PID 会变化，必须先确认 PID 对应的进程和服务归属。优先用 systemd 正常停止服务。

## 11. 第十阶段：首页 500 与数据库迁移

当健康检查通过但首页返回 500，先看应用日志：

~~~bash
docker compose -p fastapi-blog-ip \
  -f compose.public-ip.yaml logs --tail=200 app
~~~

如果最后一个数据库异常显示表不存在，执行迁移前必须确认：

~~~bash
docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml run --rm app uv run alembic heads

docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml run --rm app uv run alembic current
~~~

确认目标数据库、备份和 Revision 后，才执行写操作：

~~~bash
docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml run --rm app uv run alembic upgrade head
~~~

迁移后验证：

~~~bash
docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml run --rm app uv run alembic current
curl -fsS http://<ECS_PUBLIC_IP>/health/ready
curl -fsS -o /dev/null -w '%{http_code}\n' http://<ECS_PUBLIC_IP>/
~~~

不要使用 alembic stamp head 假装迁移完成；它只修改版本记录，不创建缺失的表。

## 12. 附件命令的“修改了哪些东西”

| 操作 | 是否修改系统 | 实际影响 |
|---|---:|---|
| pwd、ls、find、grep、cat app/core/config.py | 否 | 查看路径、文件和代码；cat app.env 会泄露 Secret |
| cat >> app.env、echo >> app.env、sudo bash -c ... | 是 | 追加生产配置；可能重复追加、格式错误或泄露密钥 |
| cp Dockerfile Dockerfile.bak | 是 | 创建备份文件，可恢复 Dockerfile |
| sed -i ... Dockerfile | 是 | 修改 Dockerfile；原记录因续行错误导致 Dockerfile 语法问题 |
| 重写 compose.production.yaml | 是 | 把正式外部 RDS/Tair 方案改成本机 PG/Redis 方案，并硬编码了密码 |
| 修改 DATABASE_URL/REDIS_URL 主机 | 是 | 从 ECS IP 改为 Compose 服务名；只适用于本机 Docker 依赖 |
| mkdir -p data/postgres data/redis | 是 | 创建数据库和 Redis 持久化目录 |
| systemctl stop/disable nginx | 是 | 停止并可能禁用宿主机 Nginx |
| docker compose up -d --build | 是 | 构建镜像、创建/重建容器、启动服务 |
| alembic upgrade head | 是 | 修改 PostgreSQL 表结构和版本记录 |
| curl、ss、docker ps、docker logs | 否 | 验证网络、端口、容器状态和应用日志 |

## 13. 一条推荐的最小排查命令链

无域名公网 IP 模式：

~~~bash
cd /opt/fastapi-blog/current
git status --short
docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml config -q
docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml ps
docker compose -p fastapi-blog-ip \
  --env-file /opt/fastapi-blog/config/compose-public-ip.env \
  -f compose.public-ip.yaml logs --tail=100 app nginx
curl -fsS http://<ECS_PUBLIC_IP>/health/live
curl -fsS http://<ECS_PUBLIC_IP>/health/ready
sudo ss -lntp | grep -E ':(80|443|8000|5432|6379)\b' || true
~~~

只有当上面结果清楚后，才进入数据库迁移、端口释放、Docker daemon 修改或配置切换。

## 14. 学习结论

这次故障最重要的不是记住某一条命令，而是学会按边界定位：

- 配置错误：看 Settings 和环境变量；
- 构建错误：看 Dockerfile、包索引和容器 DNS；
- 400：看 Host/请求协议；
- readiness 503：看 PostgreSQL、Redis 和健康接口；
- 502：看 Nginx 到 app 的连接；
- 端口冲突：看宿主机监听进程；
- 首页 500：看应用日志最后一个数据库异常；
- 表不存在：确认数据库后执行 Alembic；
- 域名访问失败：区分 DNS 解析、端口、安全组和 TLS。

排查顺序永远是：先读错误最后一段，再确认目标对象，最后才执行写操作。

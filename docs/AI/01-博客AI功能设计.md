# 博客 AI 功能设计：从准确找文章到知识助手

## 1. 需求拆解

“帮我梳理博客中关于 Vue 的文章”至少包含四件事：理解用户意图、查找真实文章、组织结果、给出可点击依据。标题和 URL 必须来自数据库，不能让模型凭记忆生成。

将问题按类型路由，效果通常比把所有内容塞进一个 Prompt 更可靠：

| 问题类型 | 示例 | 推荐处理 |
| --- | --- | --- |
| 文章发现 | 有哪些 Vue 文章？ | 数据库全文/混合检索，模型排序和归纳 |
| 内容问答 | 这几篇如何解释响应式？ | RAG 检索正文片段，带引用回答 |
| 站点操作 | 收藏第二篇 | Tool Calling，服务端鉴权后调用收藏 Service |
| 闲聊 | 你是谁？ | 简短模型回答，不检索或按策略拒答 |
| 超出知识库 | Vue 4 何时发布？ | 明确知识边界；需要时接入受控联网搜索 |

## 2. 第一版 MVP：先不用向量数据库

当前博客已有 PostgreSQL、文章标题、摘要和正文。MVP 可以先复用现有异步 SQLAlchemy 请求链：

```text
用户问题
  -> POST /api/ai/chat
  -> Router：认证、限流、Schema、流式响应
  -> AI Orchestrator Service：判断为文章搜索
  -> Post Search Service：只检索 is_published=true 的文章
  -> 模型：根据真实结果生成简短梳理
  -> 响应：answer + citations[] + request_id
```

搜索可先使用 PostgreSQL 全文检索或现有标题/正文关键词查询。若检索到 0 篇，应回答“当前博客中未找到相关已发布文章”，而不是补造标题。若模型超时，仍可降级返回结构化搜索结果。

建议响应契约：

```json
{
  "answer": "这里有 3 篇与 Vue 相关的文章……",
  "citations": [
    {"post_id": 12, "title": "Vue 响应式原理", "url": "/posts/12"}
  ],
  "conversation_id": "opaque-id",
  "request_id": "opaque-id"
}
```

## 3. 第二版：RAG

当问题变成“这些文章如何解释 Vue 响应式”时，仅返回整篇文章会超过上下文窗口且噪声很大，需要 Retrieval-Augmented Generation（检索增强生成）。

### 索引链路

```text
文章发布/更新/下架
  -> 清洗 Markdown（保留标题层级和代码语义）
  -> 按章节切块
  -> 生成 Embedding
  -> 保存 chunk、post_id、标题、章节、版本、发布状态、向量
```

切块不要只按固定字符数硬切。博客更适合按 Markdown 标题和段落切分，再用 token 数限制块大小，并保留少量重叠。代码块应尽量完整。文章更新后按内容哈希增量重建索引；文章下架后必须立即从可检索范围排除。

### 查询链路

```text
问题规范化
  -> 查询改写（可选）
  -> 关键词检索 + 向量检索
  -> 元数据过滤（已发布、权限、语言）
  -> 融合与 rerank
  -> 选取少量高相关片段
  -> 模型基于片段回答
  -> 返回片段级引用
```

对“Vue”这种明确术语，关键词搜索很强；对“页面状态如何自动更新”这种语义表达，向量搜索更强。因此建议混合检索，而不是只用向量。

### 存储选择

- 起步推荐 PostgreSQL + `pgvector`：与现有数据库和事务体系一致，维护成本低。
- 数据量和查询复杂度明显增长后，再评估 Qdrant、Milvus、Weaviate、Pinecone 或云厂商检索服务。
- Redis 可缓存热点答案、限流和短期会话，不应作为文章事实的唯一持久化来源。

## 4. 对话上下文与 Memory

先区分四种经常被混称为 memory 的东西：

| 类型 | 内容 | 建议存储 |
| --- | --- | --- |
| 当前请求上下文 | System 指令、问题、检索片段 | 仅本次模型调用 |
| 短期会话 | 最近几轮消息、会话摘要 | PostgreSQL；热点可缓存 Redis |
| 长期用户偏好 | 偏好技术栈、回答长度 | PostgreSQL，显式同意、可查看删除 |
| 业务知识 | 博客文章和元数据 | PostgreSQL + 检索索引 |

不要无限保存完整聊天并每次全部发送。应使用“最近 N 轮 + 旧对话摘要 + 当前检索证据”，并根据 token 预算裁剪。摘要也是模型生成内容，不能替代真实业务事实。

第一版不建议做长期个性化记忆。先把单轮检索准确率、引用和权限做好，再增加会话记忆。

## 5. 工具调用示例

模型可以选择 `search_posts` 工具，但真正的权限、参数校验和数据库访问仍由服务端执行：

```json
{
  "name": "search_posts",
  "description": "搜索当前用户可访问的已发布博客文章",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {"type": "string"},
      "limit": {"type": "integer", "minimum": 1, "maximum": 10}
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

模型输出的工具参数是不可信输入。服务端必须再次用 Pydantic 校验、限制最大结果数、执行鉴权、设置超时并记录审计日志。诸如“删除文章”“发邮件”一类有副作用的工具需要用户确认和幂等设计。

## 6. 可继续增加的功能

按价值和难度排序：

1. 相关文章推荐：基于标签、关键词和向量相似度，推荐理由可解释。
2. 管理员写作助手：标题建议、摘要、标签、SEO 描述；只生成草稿，必须人工确认发布。
3. 评论辅助回复：提供回复建议而非自动公开发送，降低错误和冒犯风险。
4. 语义搜索：用户不需要知道准确关键词。
5. 内容质量检查：错别字、结构、失效链接、敏感信息检查。
6. 多模态能力：为图片生成替代文本或理解文章配图；需额外评估隐私和成本。

## 7. MVP 验收指标

- 给定一组 Vue 测试问题，标题和链接必须真实存在且均为已发布文章。
- 检索不到时不虚构；引用可以点击并对应支持答案的片段。
- 越权文章、草稿和下架文章不能通过提示注入被检索出来。
- 首 token 延迟、总延迟、模型/检索失败率和单次成本可观测。
- 模型不可用时返回明确错误或搜索降级结果。
- 固定评测集覆盖直接关键词、同义表达、多轮追问、无答案和恶意提示。
